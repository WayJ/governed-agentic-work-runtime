# Governed Work Runtime

**让 Agent 自主规划，让每次业务行动都有依据。**

面向长期业务工作的持久运行时：Agent 提议行动，规则决定能否执行，证据证明是否完成。

[English](README.md) · [网站](docs/website.md) · [核心语义](docs/RFC-001-core-semantics.md) · [交互协议](docs/RFC-003-runtime-protocol.md) · [验证覆盖](docs/verification.md) · [贡献指南](CONTRIBUTING.md)

当前是本地参考原型，使用 Python 3.9+ 和标准库，Apache-2.0 许可证，无第三方运行依赖。报销与内容发布两个业务域及其 OA/发布服务适配器均为演示，不需要模型 API Key。

## 一条命令体验真实崩溃恢复

```bash
git clone https://github.com/WayJ/governed-agentic-work-runtime.git
cd governed-agentic-work-runtime
python3 -m work_runtime demo
```

演示会完成以下过程：

1. Agent 提议提交，被“缺少特别批准”阻断。
2. 工作进入持久等待，Agent 无需持续在线。
3. 财务批准当前版本内容，Runtime 保存提交意图。
4. 独立模拟 OA 受理申请后，工作进程直接退出，尚未保存响应。
5. 重启 Runtime，通过原业务键查回受理记录。
6. 验收完成；模拟 OA 数据库中的受理申请数量严格为 1。

每次运行创建新的临时目录，保留 SQLite 状态和业务事件；输出提供查看命令。

## 看签名证据如何守住发布关口

```bash
python3 -m work_runtime publish-demo
```

第二个业务域使用同一个 Runtime 类、独立的数据库。审阅批准与作者确认以 HMAC 签名信封到达：被篡改的批准在任何写入之前即被拒绝；签名有效也只生成候选证据，仍需单独核验；外部发布已提交但响应超时后，通过查询同一操作恢复，绝不重复提交。自 S14 起，同一对存储上追加撤回章节：第二份文档发布后，其工作在取消窗口内被请求取消，已发布产物经关联的 `content.unpublish` 补偿在一次真实工作进程崩溃后完成撤回。

1. Agent 提议发布，被“缺少审阅批准”阻断。
2. 被篡改的审阅批准 → EVIDENCE_AUTHENTICATION_FAILED，入库前拒绝。
3. 有效签名的批准/确认在核验前仅为候选 → 通过后发布意图成立。
4. 发布服务已提交，响应超时 → 结果未知，但产物已存在。
5. 重启 Runtime，查询同一操作 → 找回受理记录，未重发。
6. 证据齐备，验收完成；发布产物数量严格为 1。
撤回章节 — 在取消窗口内取消第二个工作，撤回其已发布产物
7. 第二份文档经同一签名关口作为独立工作进入 → 发布确认；发布产物：2。
8. 属主请求取消 — 取消窗口开启；请求本身不改已确认的发布。
9. 属主提议关联撤回（五键负载）→ 以不可变原始快照与独立业务键就绪。
10. 携带权限的子进程派发撤回 → 外部撤回已提交（RTR-…）→ 子进程在记录结果前退出（退出码 73）。
11. 重启 → recover() 按原业务键对账 → 恰好一次尝试确认成功；追加 withdrawn 证明，原始真相保留。
12. 以精确双 id 确认（发布 + 撤回）完成取消 → closed/cancelled。
2 个工作；发布产物：2；撤回效果：1；窗口内有界撤回，不是 reversal。

收尾计数由独立的发布数据库（`publications` 与 `retractions` 表）及运行时存储直接核对——2/1、带 PUB-/RTR- 外部 id 的精确双 id 确认、追加的 `withdrawn` 证明——绝不解析叙述文本；输出的 `inspect --policy content-publish` 命令可回看两个工作。这是取消窗口内的有界撤回，不是 reversal：原始发布、回执、受理证明与历史全部保留。属主的 `content.unpublish` 授权是受信任的本地配置而非身份认证；“撤回后再发布”在受治理流程内不可达（同工作永久意图拒绝、跨工作业务键冲突，该交互只约束适配器模型）。签名只证明来源真实性与内容完整性，不证明业务事实，边界见[签名证据文档](docs/signed-evidence.md)与[干预文档](docs/interventions.md)。

## 看干预如何停住工作而不丢外部效果

```bash
python3 -m work_runtime intervention-demo
```

三个干预场景运行在同一个 Runtime 类上，各自使用一对全新数据库：

1. **所有权转移（transfer/）**：Agent 的提交意图在转移给 delegate 后被显式作废（`OWNERSHIP_TRANSFERRED`）；旧所有者重新提议、重放已受理命令均被拒绝且原始回执保持不变；新所有者重提同一操作（业务键不变）并成功派发。
2. **取消与未知外部效果（cancel/）**：外部已受理但响应丢失时申请取消，效果未查明前无法终结（`OUTCOME_UNRESOLVED`）；按原业务键查询恰好找回一次效果（`CANCEL_ACKNOWLEDGEMENT_MISMATCH` 钉死精确确认集合），最终以精确确认关闭为 cancelled——效果被如实记录，绝不被“反转”。
3. **显式策略迁移（migrate/）**：管理员把工作从 demo-1 显式迁移到更强的 demo-2：旧批准失效、E05 变为必须满足、合同修订号递增；未加载版本注册表时重启直接拒绝读取（fail closed）；新的版本绑定批准到达后同一操作被重新接纳并派发。

每个场景的外部数据库独立核对：意图仅被准备或作废时外部调用为 0，外部受理后恰好 1 条受理申请；末行 `accepted applications: 3 (one per store)` 由三个库分别计数断言。取消确认是持久记账，不是补偿——没有任何效果被反转。授权映射中的所有者、代办与管理员都是受信任的本地主体，不是远程身份认证。绑定 demo-2 的工作必须以 `inspect --policy-versions demo-1,demo-2` 显式加载版本注册表才能查看；缺省检查保持原行为、直接拒绝读取。

## 上手采用：静态检查规则卡，真实发布一个文件

```bash
python3 -m work_runtime adoption-demo
python3 -m work_runtime lint-sop work_runtime/data/sop/publishing.json
```

第四个演示就是新贡献者的采用路径。静态序幕先做 SOP 规则卡检查：一张故意无效的卡给出有界诊断，两张随包发行的卡检查通过并输出精确的 SHA-256 内容摘要；同时明确声明“被检查的 JSON 永远不会被 Runtime 执行”。随后在不变的 Runtime 与发布策略上，以 HMAC 签名的审阅/作者证据接入第三个适配器 `FilePublisher`：批准并核验之后，一个真实的哈希命名 JSON 产物提交到全新目录；随后响应丢失（组合包装器在真实提交之后抛出超时），重启的 Runtime 通过查询原业务键恢复结果——绝不重复提交。

1. 无效演示卡 → 3 条诊断，第一条 EMPTY_VALUE 位于 /policy/goal（lint-sop 退出码 1）。
2. 随包规则卡检查通过并给出精确内容摘要（退出码 0）。
3. Agent 提议发布 → 被 C02（缺少审阅批准）阻断。
4. 被篡改的审阅批准 → EVIDENCE_AUTHENTICATION_FAILED，入库前拒绝。
5. 有效签名的批准/确认在核验前仅为候选 → 通过后意图成立。
6. FilePublisher 提交真实的哈希命名产物；提交后响应丢失 → 结果未知。
7. 重启 → 按原业务键对账 → confirmed_succeeded，未重发。
8. 证据齐备，验收完成；已提交文件产物：1。

末行计数直接对着发布目录核对（恰好一个 `[0-9a-f]{64}.json` 文件）；输出中的 `inspect` 命令与产物路径可原样执行。`lint-sop` 退出码为 0 干净 / 1 有诊断 / 2 文件级错误（重复对象键、非有限数值、非法 UTF-8、畸形 JSON、不可读或超过 1 MiB 均为退出码 2，且绝不回显文件内容）；`--json` 输出精确的 static-only 结果信封。静态检查只做结构评审——不执行任何文本谓词，也不授予发布权限。想自行扩展本运行时（通过公开一致性测试实现第三方风格适配器，或编写受评审的规则卡），请阅读[贡献者指南](docs/contributor-guide.md)。

## 撤销证据而不抹去历史

```bash
python3 -m work_runtime revocation-demo
```

第五个演示在同一个 Runtime 上、两个策略族中演练证据撤销，每个场景各用一对全新数据库。已核验的批准通过版本绑定的 `revoke_evidence` 命令撤销，负载严格为 `{source, event_id, reason}`：随后已准备的意图在派发时被挂起（外部调用为 0），新事件号下的替代批准以同一业务键重新接纳同一操作。第二个场景围绕一次不确定的外部效果撤销证据：已提交的申请恰好保留一次——按原业务键对账找回、绝不重发、确认后绝不再执行，证据撤销期间验收保持阻断。第三个场景先完成一次发布再撤销其受理证明：历史完成快照逐字节不变，当前要求重新变为待满足，`EvidenceRevoked` 事件如实记录 `work_was_closed` 与 `completion_cites_evidence`。

1. **持有（hold/）**：财务批准被撤销 → 再提议被拒（`REQUIREMENT_UNSATISFIED`）；派发被挂起、零次外部调用；重放撤销命令返回原回执；重发同一来源事件只报 `evidence_status "revoked"`；替代批准（新事件号）→ 同一操作重新接纳 → 派发成功，本库受理申请恰好 1 条。
2. **不确定效果（uncertain/）**：外部已受理但响应丢失 → 按原业务键对账确认，未重发；管理员撤销受理证明、财务撤销批准后，重新提议仍返回已确认的同一操作（确认的效果绝不再执行以再生证明）；验收被 `REQUIREMENT_UNSATISFIED`（E05、E08）阻断，受理申请仍恰好 1 条。
3. **关闭后纠正（publish/）**：审阅批准撤销 → 发布被挂起、零产物；替代批准 → 同一操作重新接纳并发布恰好 1 件；验收关闭后管理员撤销受理证明 → 结果与完成快照逐字节不变、C04 重新待满足；重发被撤销的批准事件仍报 `revoked`，产物仍恰好 1 件。

末行 `retained external effects: 2 accepted applications, 1 published artifact; effects reversed: 0` 由三个外部数据库分别计数断言。撤销只收回当前有效性：绝不改写回执、关闭快照或外部效果，也不是补偿——"effects reversed: 0" 是实测计数。可撤销主体是该工作当前配置的证据来源（持 `evidence.revoke` 权限）或 `work.intervene` 管理员——均为受信任的本地授权，不是身份认证；撤销不能阻止已在途的外部调用。详见[证据撤销文档](docs/evidence-revocation.md)。

## 撤回已受理的报销——补偿而非抹除

```bash
python3 -m work_runtime compensation-demo
```

第六个演示演练 S10 的受限补偿切片：只在取消窗口内执行的报销撤回。前向报销先被受理（回执、发票与证明俱全）；`request_cancel` 之后所有者提议关联撤回（`compensates` = 已确认的原操作 id），运行时以独立稳定业务键保存不可变的原始快照。一个携带权限的子进程派发该撤回，并在外部撤回效果提交后真实崩溃；重启的运行时按原业务键对账恢复——恰好一次尝试、绝不重发。撤回追加一种独立的 `withdrawn` 证明；原受理回执与 E08 满足状态原样保留——历史只追加、绝不删除。关闭时按精确的两个成功 id（原件 + 撤回）确认。第二个场景把撤回指向从未见过原件的外部库：适配器给出可查询的权威拒绝 `ORIGINAL_ABSENT`，运行时记录 `confirmed_failed` 并把拒绝原因存入 `adapter_result`，关闭确认只包含保留的原件——拒绝是显式事实，既不是反转也不是未知；未决补偿阻断关闭，不会被放弃。

1. **真实崩溃（crash/）**：单据核验齐全 → 前向提交被 OA 受理；管理员请求取消 → 所有者提议关联撤回（五键负载），获得不可变原始快照 `{operation_id, external_id, capability}` 与独立稳定业务键；携带 `expense.withdraw` 权限的子进程派发，外部撤回效果（WD-…）提交后子进程以 exit code 73 真实死亡；重启后 `recover()` 按原业务键对账，恰好一次尝试确认成功；只读读回：原受理证明仍为 verified、E08 仍满足，撤回追加了独立的 withdrawn 证明与本库第 2 张回执——受理申请 1、撤回效果 1，历史只追加；管理员以精确双 id 确认关闭（closed/cancelled），关闭处置携带 compensates 与存储的 adapter_result。
2. **权威拒绝（refusal/）**：全新库中前向报销受理确认后请求取消、准备关联撤回；派发面向从未见过原件的第二个外部库（absent.sqlite）→ 适配器返回可查询的权威拒绝 ORIGINAL_ABSENT（零撤回效果）；运行时记录 confirmed_failed，拒绝原因存入 adapter_result；关闭确认只包含保留的原件（ack 恰好 1 个 id），关闭处置保留拒绝——拒绝不是反转，原效果仍在；本库受理申请 1、撤回效果 0、拒绝回执 1。

每个计数都由场景自己的外部数据库断言。执行撤回的是一个携带权限的子进程——随包 `worker` 命令行硬编码演示权限（不含 `expense.withdraw`），经它派发撤回只会被 AUTHORITY_DENIED 挂起、零次尝试零效果（有专门测试钉住这一边界）。本切片仅限取消窗口内的补偿：报销族在此演示，发布族自 S14 起由上方 `publish-demo` 撤回章节演示；关闭后补偿、链式与公开的放弃命令均未实现；拒绝或未知绝不改写原效果，withdrawn 证明不能经入口导入、仅管理员可撤销；主体均为受信任的本地授权，不是身份认证。详见[干预文档](docs/interventions.md)。

## 轮换来源签名密钥而不改写历史

```bash
python3 -m work_runtime rotation-demo
```

第七个演示演练 S11 的来源签名密钥轮换。来源持有一个密钥环——具名密钥、显式 `current` 项与含端点的有效期窗口；信封可通过参与签名内容的 `key_id` 指定用哪把密钥。演示在注入的确定性时钟与临时内存密钥上运行（只打印密钥 id，绝不打印密钥本身）：双密钥窗口内两把密钥均可认证；轮换把 current 切到新密钥并让旧密钥保留一个宽限窗口——在窗口边界上重放原始信封仍取回其缓存回执；宽限期一过，同一信封被拒绝 `EVIDENCE_KEY_RETIRED`——认证先于命令缓存，存储回执不可达、零写入；以新密钥重签同一 command id 逐字节返回原始缓存回执（无新行）；同一事件的新 command id 报告当前状态并恰好新增一行命令；六表历史摘要证明轮换动作未写入任何内容。

```text
Scenario — 轮换来源签名密钥而不改写历史（独立存储：rotate/）
临时内存密钥 finance-2026-08（current）与 finance-2026-10；绝不打印密钥本身，只打印密钥 id
1. 双密钥窗口：两把密钥签名的批准在同一密钥环下认证通过 → accepted（pending_verification）
2. verify_pending → 两个批准均核验（轮换前最后一次合法写入）
   six-table digest before rotation: <16位十六进制摘要>
3. 轮换：finance-2026-10 成为 current，finance-2026-08 保留 not_after = T+300（宽限 == max_age）；时钟停在边界 → 重放原始旧密钥信封 → 原始缓存回执原样返回，零写入
4. 时钟过宽限一秒：同一原始信封 → 拒绝 EVIDENCE_KEY_RETIRED（密钥窗口先于新鲜度；缓存回执在认证之后不可达），零写入
5. 以新密钥重签，同一 command id 与业务负载（刷新时间戳）→ 原始缓存回执逐字节一致；无新命令行，零写入
6. 新 command id，同一来源事件 → accepted；evidence_status "verified"（当前状态）；恰好新增一行命令，无新证据行
7. 全部步骤后的六表摘要：<16位十六进制摘要>——边界重放、退役拒绝与重签期间，六表与轮换前逐字节一致；新命令恰好追加一行 commands（其余五表仍逐字节一致）
1 scenario; dual-key accepts: 2; retired refusals: 1 (zero writes); cached receipts verbatim: 2; new commands: 1; history rewritten: 0
```

每个论断都对着演示自己的 SQLite 存储断言——摘要、状态、指纹与命令行数由测试和已安装校验器本地重算，绝不解析旁白文本。轮换是纯配置信任：密钥环配置是密钥身份的唯一载体——哪把密钥认证了证明永不入库，没有持久的吊销记忆或轮换审计，重新部署轮换前配置会复活旧密钥（回滚与退役 key_id 复用是运维纪律）；被攻破的 current 密钥在轮换落地且宽限期结束前仍可伪造；时钟信任归运维所有。这一切都不是租户认证、TLS、外部 KMS、分布式吊销或任何安全认证。详见[签名证据文档](docs/signed-evidence.md)。

## 以受治理流程发布 SOP 规则卡

```bash
python3 -m work_runtime publication-demo
```

第八个演示演练 S12 的受治理 SOP 规则卡发布核心（设计 D54–D66），以及 S13 起加入的受治理撤回章节（D67–D79）。一次发布是恰好一个不可变的哈希命名产物，位于对卡片精确内容摘要的签名版本绑定批准之后，走与其他外部效果相同的命令协议。演示无凭据、在注入的确定性时钟与临时内存批准密钥上运行（只打印密钥 id，绝不打印密钥本身）：故意无效的卡被检查拒绝；随包 `publishing.json` 检查通过并携带固定摘要，成为工作文档；提案因缺少批准被阻断；被篡改的 `card_approval` 在任何写入之前被拒绝 `EVIDENCE_AUTHENTICATION_FAILED`；合法的签名 `{digest, policy_version}` 批准核验通过，意图被接受，业务键即基于摘要的发布键；派发恰好提交一个产物后丢失响应；重启后一次尝试按原键对账恢复 `confirmed_succeeded`；`accepted` 证明由运行时在存储来源下写入（`event_id` = 操作 id）；完成关闭工作 `succeeded`；同一版本的篡改卡先被 `REQUIREMENT_UNSATISFIED` 阻断（钉住的 D66 顺序），只有在它自己的批准之后才持久化 `OPERATION_CONTENT_CONFLICT`，获胜产物的字节不变；加载器返回摘要匹配的卡片，而缺失版本与被篡改文件以可区分的有界错误拒绝关闭；批准密钥轮换后，新鲜的旧密钥信封被拒绝 `EVIDENCE_KEY_RETIRED`，六张运行时表与产物字节原封不动。随后的撤回章节走同一受治理流程结束该版本的当前有效性：封闭撤回请求作为独立工作进入，先因缺少 `card_withdrawal` 批准被阻断（W02，D66 顺序）；来自轮换后当前密钥的合法签名批准使意图被接受，业务键即撤回键；派发恰好提交一个新的哈希命名产物（撤回记录），发布产物字节不变，存储受理满足 W03、完成关闭撤回工作 `succeeded`；加载器随即以独立的 withdrawn 错误拒绝该版本；`withdrawal_record()` 读回确切记录；已撤回版本的重发布在其自身批准之后被拒 `OPERATION_CONTENT_CONFLICT`，零次存储写入；新鲜的旧密钥撤回信封被拒绝 `EVIDENCE_KEY_RETIRED`，六张表与两份产物原封不动。演示还会打印发布与撤回两个工作的 `inspect --db … --policy sop-publish` 命令（该选项加载发布策略族）与两份已提交产物路径。

每个计数都对着演示自己的 SQLite 存储与产物目录断言——键、摘要、状态与回执由测试和已安装校验器本地重算，绝不解析旁白文本；植入标记测试证明密钥永不出现在输出中。边界即设计的边界：批准者与发布者是权限配置中的受信任本地主体，不是身份认证；信任纯来自配置（配置回滚会复活退役密钥）；没有"取消撤回"——撤回记录存续期间该版本的错误答案永久有效，修正的卡以新版本字符串发布；已发布的卡片绝不执行（加载器与固定摘要是显式运维检查，无 Runtime 接线）；这一切都不是租户认证、TLS、外部 KMS、网络访问或分布式恰好一次声明。详见[SOP 编写文档](docs/sop-authoring.md)。

## 提交一张客户工单：未知阻断准入，崩溃后按引用恢复

```bash
python3 -m work_runtime support-demo
```

第九个演示在冻结的命令面上运行第三个业务家族——客户工单：家族交付期间 `work_runtime/runtime.py` 与 `work_runtime/adapters.py` 保持字节不变（S15 冻结结论，SHA-256 基准记录在冲刺证据中）。第一章在分诊前提交一张账务工单：严重级别与类别未决时提案被 `APPLICABILITY_UNRESOLVED` 阻断——未知绝不等同于符合政策，未决的严重级别同时使 SLA 规则的适用性保持未知。分诊修订单据（severity=critical、category=billing）后，服务台在 critical 预算内承诺 45 分钟 SLA，准入以工单引用本身作为业务键通过——键中不含内容摘要。派发在 GitHub 工单形状的本地模拟追踪器中立出 issue `#1`；追踪器来源的受理证据满足目标，工作以 succeeded 关闭。第二章由携带授权的子进程派发第二张工单，并在追踪器受理写入后真实崩溃（退出码 73）；重启后的 Runtime 按工单引用业务键 `recover()`——找回原始回执、恰好一次尝试、零重发——第二件工作随之关闭。追踪器对每个工单引用只保留一个 issue：相同内容换键复用同一编号，已用引用下的变更内容是可查询的业务拒绝 `TICKET_REFERENCE_CONTENT_CONFLICT`，在受治理流程中则于提案时呈现为 `OPERATION_CONTENT_CONFLICT`——一个引用，一次受治理派发。每个打印计数都直接对 SQLite 存储断言；无需凭据、服务或密钥。见[适配器契约](docs/adapter-contract.md)与[运行时边界](docs/runtime-boundaries.md)。

## 运行混合节点工作流：Agent、人工与自动节点

```bash
python3 -m work_runtime workflow-demo
```

第十个演示在同一件受治理的工作里混合多种节点类型。场景是**已发布的数据**而不是
代码：包含十一个节点的定义、执行人、审核权限、能力与校验器都绑定到内容摘要，因此任何
绑定都能对照它当初钉住的那份字节逐字核对。Agent 整理材料，第一位审核人批准后运行时
**自行**创建第二位审核人的待办——中间没有任何 Agent 回合——第二位审核人批准后运行时
只派发一次外部动作，责任人提交处理反馈，独立复核人复核后运行时用稳定的请求标识把
**原会话**的 Agent 工作排入队列，Agent 写出报告且只有在独立评阅证据到达后才完成，
最后由运行时交付产物。派发动作的 worker 是真实进程，它在外部效果落库后真的退出
（exit 73）；重启后运行时查询原操作而不是重复执行。外部效果在替身业务系统自己的库
里计数：一次派发、一次交付。执行人永远不能批准自己，候选结果只有被已注册、版本钉住的
校验器接受才算数，过期的决定永远不满足节点。

最后一章是**验收**：受信任的 runner 接受已结束的工作流，被接受的精确最终快照被冻结
——模板摘要、契约与计划版本、文档与对象版本、每个节点尝试及其判定、每次效果与每项
义务——此后对材料的再次修改被拒绝，因为已验收的工作流是冻结的。平台关闭自己的任务
依据的是这次验收，而不是那句可变的"已结束"读数。

自动节点、人工节点与等待节点同样受质量管控：外部系统真实返回的回执连同其来源被留存，
其中的业务载荷先由声明的、版本钉住的校验器判定，通过后才成为具名工作流对象。派发回执
成为处理反馈与独立复核所审阅的**订单**，而等待节点只接受它绑定的那一次尝试的证明——
旧证明永远不满足新的尝试。人工决定可以携带它产出的具名记录（签认记录、处理反馈、
独立复核结论），该记录与决定在同一条命令内被判定并写入，因此安全审核人自己的签认
记录就是项目批准人读到的材料。效果与输出是两件事：输出校验失败不会被谎报成外部失败，
那次效果也永远不会被再执行一次。没有声明质量的节点会明说自己未被检查，而不会暗示
它已被检查。详见[混合节点工作流运行时](docs/workflow-runtime.md)、
[接口契约](docs/workflow-api-contract.md)与[运行时边界](docs/runtime-boundaries.md)。

## 这套模型解决什么

业务工作可能跨越数天、多个会话和外部系统。计划可以修订，但必须履行的要求不会因删掉计划步骤而消失；一次调用超时，也不能意味着现实世界没有发生操作。

Runtime 管理 Work 的持久状态、规则评估、命令回执、操作身份、证据和等待。Agent 基于这些状态提出下一步，而不直接修改“已批准”或“已完成”。

当前已实现两层操作去重、外部事件去重、对象版本匹配、未知条件阻断、等待恢复、派发前授权检查，以及外部结果核实；另有 HMAC 签名证据入口（信封校验、按源配置密钥或具名密钥环——S11 轮换：可选签名 `key_id` 选择符与含端点有效期窗口、双密钥窗口、先于缓存的 `EVIDENCE_KEY_RETIRED` 退役拒绝、重签命令逐字节返回原缓存回执而不改写历史——新鲜度与防篡改先于任何写入，保留的 `accepted` 种类不能经入口提交）、适配器能力声明与可复用一致性测试、第二个业务域（内容发布）、显式干预生命周期：所有权转移（作废准备意图、回放前复查授权）、取消（未知效果必须先查询、按精确集合确认已成功效果并记录外部编号、绝不宣称反转）与同族策略显式迁移（按工作锁定版本、重启未加载即拒绝、迁移时在目标策略下重验全部证据），显式证据撤销（版本绑定 `revoke_evidence` 命令，负载严格 `{source, event_id, reason}`：已撤销证据永不复活、重发只报当前状态；被挂起意图零外部调用、替代证明以同一业务键重新接纳、已确认效果与关闭快照逐字节保留），静态 SOP 规则卡检查（确定性诊断与精确内容摘要，随包示例卡随包发行——仅结构评审，绝非可执行权限），受治理的 SOP 规则卡发布与撤回（S12/S13：检查通过的卡片在签名版本绑定 `{digest, policy_version}` 批准之后，经不变的命令协议提交为恰好一个不可变哈希命名产物——基于摘要的发布键（每卡片版本一个产物）、响应丢失后一次对账恢复、运行时写入的受理证明、同版本篡改内容只在其自身批准后冲突、无 Runtime 接线的拒绝式加载器与固定摘要、S11 语义的批准密钥轮换；已发布版本的当前有效性可经同一受治理流程撤回——签名 `card_withdrawal`、第二份不可变撤回记录产物、独立的 withdrawn 加载器错误、重发布被拒且零次存储写入；无"取消撤回"：修正只能以新版本字符串发布，已发布卡片绝不执行），第三个真实文件系统适配器 `FilePublisher`（每个幂等键恰好一个不可变的哈希命名 JSON 产物，原子提交、重启可查，配上无凭据采用演示），受限报销补偿（S10：取消窗口内以独立业务键与不可变原始快照执行关联的 expense.withdraw 撤回，追加 withdrawn 证明并保留原历史，缺失原件为可查询的 ORIGINAL_ABSENT 权威拒绝，关闭按精确成功 id 集合确认——无通用反转、无放弃命令；自 S14 起同一关联流程覆盖发布族，`content.unpublish` 配对 `content.publish`，由 `publish-demo` 撤回章节演示），以及离线只读操作界面（`ui`/`ui-demo`：面向持久记录的中英双语轻量界面——磁贴、可搜索列表、要求/证据/操作/决策/事件/文档详情、存储 JSON 原文文本化渲染，附真实命令五工作样例与随包静态资源）。报销与发布规则均可通过 `Policy` 接口替换；工具执行与结果查询通过 `Adapter` 接口接入；自行扩展请阅读[贡献者指南](docs/contributor-guide.md)。

当前接口只面向受信任的本地应用代码。示例中的主体名称和权限配置不构成远程身份认证——所有者与 `work.intervene` 管理员是受信任的本地主体；签名入口只在配置的共享密钥边界内认证证据来源，不是传输安全、租户授权或业务事实证明。每个运行时数据库归属一个策略族，工作可通过显式加载的版本注册表锁定该族的不同版本，两个演示域使用各自数据库。分布式执行、多租户授权、已撤回发布的"取消撤回"（存储只追加，修正以新版本发布）、卡片到策略的执行绑定、通用补偿（效果反转）、在途外部调用的隔离（fencing）尚未实现：取消与撤销都只如实保留外部效果。受限例外是 S10/S14 关联补偿：取消窗口内关联的补偿能力（`expense.withdraw`，自 S14 起还有 `content.unpublish`）作为独立外部操作执行并记录 `withdrawn` 证明，原效果历史保持不变——关闭后与链式补偿仍未实现，“撤回后再发布”在受治理流程内不可达（仅约束适配器模型）；完整范围见[验证报告](docs/verification.md)。
