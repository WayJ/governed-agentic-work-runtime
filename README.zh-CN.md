# Governed Work Runtime

**让 Agent 自主规划，让每次业务行动都有依据。**

面向长期业务工作的持久运行时：Agent 提议行动，规则决定能否执行，证据证明是否完成。

[English](README.md) · [核心语义](docs/RFC-001-core-semantics.md) · [交互协议](docs/RFC-003-runtime-protocol.md) · [验证覆盖](docs/verification.md) · [贡献指南](CONTRIBUTING.md)

当前是本地参考原型，使用 Python 3.9+ 和标准库，Apache-2.0 许可证，无第三方运行依赖。报销与内容发布两个业务域及其 OA/发布服务适配器均为演示，不需要模型 API Key。

## 一条命令体验真实崩溃恢复

```bash
git clone https://github.com/WayJ/governed-agentic-work-runtime.git
cd governed-agentic-work-runtime
python3 -m work_runtime demo
```

演示会完成以下过程：

1. Agent 提议提交，被“缺少特别批准”阻断。
2. 工作进入持久等待，Agent 无需持续在线。
3. 财务批准当前版本内容，Runtime 保存提交意图。
4. 独立模拟 OA 受理申请后，工作进程直接退出，尚未保存响应。
5. 重启 Runtime，通过原业务键查回受理记录。
6. 验收完成；模拟 OA 数据库中的受理申请数量严格为 1。

每次运行创建新的临时目录，保留 SQLite 状态和业务事件；输出提供查看命令。

## 看签名证据如何守住发布关口

```bash
python3 -m work_runtime publish-demo
```

第二个业务域使用同一个 Runtime 类、独立的数据库。审阅批准与作者确认以 HMAC 签名信封到达：被篡改的批准在任何写入之前即被拒绝；签名有效也只生成候选证据，仍需单独核验；外部发布已提交但响应超时后，通过查询同一操作恢复，绝不重复提交。

1. Agent 提议发布，被“缺少审阅批准”阻断。
2. 被篡改的审阅批准 → EVIDENCE_AUTHENTICATION_FAILED，入库前拒绝。
3. 有效签名的批准/确认在核验前仅为候选 → 通过后发布意图成立。
4. 发布服务已提交，响应超时 → 结果未知，但产物已存在。
5. 重启 Runtime，查询同一操作 → 找回受理记录，未重发。
6. 证据齐备，验收完成；发布产物数量严格为 1。

末行数字由独立的发布数据库（`publications` 表）核对；输出中的 `inspect --policy content-publish` 命令可回看持久状态。签名只证明来源真实性与内容完整性，不证明业务事实，边界见[签名证据文档](docs/signed-evidence.md)。

## 看干预如何停住工作而不丢外部效果

```bash
python3 -m work_runtime intervention-demo
```

三个干预场景运行在同一个 Runtime 类上，各自使用一对全新数据库：

1. **所有权转移（transfer/）**：Agent 的提交意图在转移给 delegate 后被显式作废（`OWNERSHIP_TRANSFERRED`）；旧所有者重新提议、重放已受理命令均被拒绝且原始回执保持不变；新所有者重提同一操作（业务键不变）并成功派发。
2. **取消与未知外部效果（cancel/）**：外部已受理但响应丢失时申请取消，效果未查明前无法终结（`OUTCOME_UNRESOLVED`）；按原业务键查询恰好找回一次效果（`CANCEL_ACKNOWLEDGEMENT_MISMATCH` 钉死精确确认集合），最终以精确确认关闭为 cancelled——效果被如实记录，绝不被“反转”。
3. **显式策略迁移（migrate/）**：管理员把工作从 demo-1 显式迁移到更强的 demo-2：旧批准失效、E05 变为必须满足、合同修订号递增；未加载版本注册表时重启直接拒绝读取（fail closed）；新的版本绑定批准到达后同一操作被重新接纳并派发。

每个场景的外部数据库独立核对：意图仅被准备或作废时外部调用为 0，外部受理后恰好 1 条受理申请；末行 `accepted applications: 3 (one per store)` 由三个库分别计数断言。取消确认是持久记账，不是补偿——没有任何效果被反转。授权映射中的所有者、代办与管理员都是受信任的本地主体，不是远程身份认证。绑定 demo-2 的工作必须以 `inspect --policy-versions demo-1,demo-2` 显式加载版本注册表才能查看；缺省检查保持原行为、直接拒绝读取。

## 上手采用：静态检查规则卡，真实发布一个文件

```bash
python3 -m work_runtime adoption-demo
python3 -m work_runtime lint-sop work_runtime/data/sop/publishing.json
```

第四个演示就是新贡献者的采用路径。静态序幕先做 SOP 规则卡检查：一张故意无效的卡给出有界诊断，两张随包发行的卡检查通过并输出精确的 SHA-256 内容摘要；同时明确声明“被检查的 JSON 永远不会被 Runtime 执行”。随后在不变的 Runtime 与发布策略上，以 HMAC 签名的审阅/作者证据接入第三个适配器 `FilePublisher`：批准并核验之后，一个真实的哈希命名 JSON 产物提交到全新目录；随后响应丢失（组合包装器在真实提交之后抛出超时），重启的 Runtime 通过查询原业务键恢复结果——绝不重复提交。

1. 无效演示卡 → 3 条诊断，第一条 EMPTY_VALUE 位于 /policy/goal（lint-sop 退出码 1）。
2. 随包规则卡检查通过并给出精确内容摘要（退出码 0）。
3. Agent 提议发布 → 被 C02（缺少审阅批准）阻断。
4. 被篡改的审阅批准 → EVIDENCE_AUTHENTICATION_FAILED，入库前拒绝。
5. 有效签名的批准/确认在核验前仅为候选 → 通过后意图成立。
6. FilePublisher 提交真实的哈希命名产物；提交后响应丢失 → 结果未知。
7. 重启 → 按原业务键对账 → confirmed_succeeded，未重发。
8. 证据齐备，验收完成；已提交文件产物：1。

末行计数直接对着发布目录核对（恰好一个 `[0-9a-f]{64}.json` 文件）；输出中的 `inspect` 命令与产物路径可原样执行。`lint-sop` 退出码为 0 干净 / 1 有诊断 / 2 文件级错误（重复对象键、非有限数值、非法 UTF-8、畸形 JSON、不可读或超过 1 MiB 均为退出码 2，且绝不回显文件内容）；`--json` 输出精确的 static-only 结果信封。静态检查只做结构评审——不执行任何文本谓词，也不授予发布权限。想自行扩展本运行时（通过公开一致性测试实现第三方风格适配器，或编写受评审的规则卡），请阅读[贡献者指南](docs/contributor-guide.md)。

## 浏览持久历史：本地只读 GUI

```bash
python3 -m work_runtime ui-demo                            # 播种五工作样例库并启动界面
python3 -m work_runtime ui --db <已有的-runtime.sqlite>    # 打开既有存储
```

命令打印实际的环回地址，`Ctrl-C` 干净退出。页面是一个离线、零依赖的中英双语查看器，只展示存储中真实记录的内容：带定义说明的指标磁贴、可搜索/筛选的工作列表，以及每项工作的当前要求、证据、操作与尝试、持久化命令决策、按键序分页的事件时间线、按原文显示的文档 JSON。所有存储载荷只按文本渲染——从不解析、绝不执行——字符串形式的整数逐位保留。`ui-demo` 通过真实命令与真实 FakeOA 播种五工作样例（等待、保留外部效果的不确定、转移、成功、确认效果后取消）；详见 [GUI 指南](docs/gui.md)。查看器以只读方式在环回地址打开存储；该绑定是便利性设计，不是认证。界面服务需要安装中已组装的只读后端模块——没有它时 `ui` 命令以有界信息退出码 2 退出，其余命令不受影响。

## 这套模型解决什么

业务工作可能跨越数天、多个会话和外部系统。计划可以修订，但必须履行的要求不会因删掉计划步骤而消失；一次调用超时，也不能意味着现实世界没有发生操作。

Runtime 管理 Work 的持久状态、规则评估、命令回执、操作身份、证据和等待。Agent 基于这些状态提出下一步，而不直接修改“已批准”或“已完成”。

当前已实现两层操作去重、外部事件去重、对象版本匹配、未知条件阻断、等待恢复、派发前授权检查，以及外部结果核实；另有 HMAC 签名证据入口（信封校验、按源配置密钥、新鲜度与防篡改先于任何写入，保留的 `accepted` 种类不能经入口提交）、适配器能力声明与可复用一致性测试、第二个业务域（内容发布）、显式干预生命周期：所有权转移（作废准备意图、回放前复查授权）、取消（未知效果必须先查询、按精确集合确认已成功效果并记录外部编号、绝不宣称反转）与同族策略显式迁移（按工作锁定版本、重启未加载即拒绝、迁移时在目标策略下重验全部证据），静态 SOP 规则卡检查（确定性诊断与精确内容摘要，随包示例卡随包发行——仅结构评审，绝非可执行权限），第三个真实文件系统适配器 `FilePublisher`（每个幂等键恰好一个不可变的哈希命名 JSON 产物，原子提交、重启可查，配上无凭据采用演示），以及离线只读操作界面（`ui`/`ui-demo`：面向持久记录的中英双语轻量界面——磁贴、可搜索列表、要求/证据/操作/决策/事件/文档详情、存储 JSON 原文文本化渲染，附真实命令五工作样例与随包静态资源）。报销与发布规则均可通过 `Policy` 接口替换；工具执行与结果查询通过 `Adapter` 接口接入；自行扩展请阅读[贡献者指南](docs/contributor-guide.md)。

当前接口只面向受信任的本地应用代码。示例中的主体名称和权限配置不构成远程身份认证——所有者与 `work.intervene` 管理员是受信任的本地主体；签名入口只在配置的共享密钥边界内认证证据来源，不是传输安全、租户授权或业务事实证明。每个运行时数据库归属一个策略族，工作可通过显式加载的版本注册表锁定该族的不同版本，两个演示域使用各自数据库。分布式执行、多租户授权、规范发布、证据撤销、补偿（效果反转）执行尚未实现：取消只确认外部效果，不撤销它们；完整范围见[验证报告](docs/verification.md)。

## 本地验证

```bash
python3 -m unittest discover -s tests -v             # 测试门禁
python3 scripts/check_docs.py                        # 文档门禁：本地链接可解析
python3 -m work_runtime demo                         # 演示门禁：真实崩溃恢复
python3 -m work_runtime publish-demo                 # 演示门禁：签名证据发布
python3 -m work_runtime intervention-demo            # 演示门禁：转移、取消、迁移
python3 -m work_runtime adoption-demo                # 演示门禁：规则卡检查 + 文件适配器采用
python3 -m compileall -q work_runtime tests scripts  # 语法门禁
python3 scripts/verify_install.py                    # 全新虚拟环境安装，并在仓库外运行模块与控制台入口演示
```

`scripts/verify_install.py` 在临时目录创建全新虚拟环境并真实安装本包：断言导入来自该环境而非当前检出、未安装任何第三方依赖，并在仓库外以模块入口运行全部四个演示（`demo`、干预与采用演示另经控制台入口复验；`publish-demo` 没有控制台阶段），最终独立核对模拟 OA 数据库受理申请数量为 1、发布数据库产物数量为 1、三个干预场景库各自恰好 1 条受理申请；对采用演示的模块与控制台双入口，各自独立枚举发布目录（恰好 1 个哈希命名产物文件）并仅用标准库重新解析校验摘要、回执、业务键与工作结果，不信任任何打印文本；同时确认随包 SOP 规则卡与 GUI 静态资源确实进入安装、已安装的 `lint-sop` 能复现固定的内容摘要；当安装中包含只读 UI 后端模块时，另以真实子进程在仓库外驱动已安装的 `ui-demo`/`ui` 入口做真实 HTTP 校验（资源逐字节一致、五工作数据、存储表不变、干净中断退出），否则打印明确的 SKIPPED 行。安装阶段需要 pip 索引访问以获取构建后端。

测试包含实际子进程崩溃、并发重复请求、单据变化后旧批准失效、跨 Work 发票唯一约束，以及无法查询外部结果时转人工介入。协议验收项 P01–P15 中 14 项由命名测试覆盖，P13（分布式租约）明确延期；逐项证据见[验证报告](docs/verification.md)。
