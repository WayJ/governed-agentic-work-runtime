# 参考业务场景与执行轨迹 v0.1

日期：2026-10-13 · 状态：桌面推演，尚未实现或执行测试

语义依据：[RFC-001](RFC-001-core-semantics.md)。所有金额、规则与接口能力均为设计假设，不代表真实企业制度。

## 1. 共用条件

场景 A、B 的目标是“当前报销单获 OA 正式受理”；场景 C 的目标是“当前报销单审批通过”。均不包含付款。每个场景建立独立 Work。

示例规则：

- 所有纳入申请的发票须有有效核验结果，不得重复报销。
- 按已绑定政策计算可报销额度；超额时须在正式提交前取得特别批准。
- 用户确认必须覆盖最终单据内容。
- 核验异常可按制度补充材料，但人工不能无依据地把无效发票改成有效。
- OA 受理必须以可查询的业务记录证明；审批通过必须由指定审批系统证明。

假设 OA 支持按业务键查询，且对同一业务键与相同内容提供有明确有效期的幂等提交；全局防重复由 OA 的唯一约束保证。缺少这些能力时，适用 RFC 的未知结果与跨 Work 限制。

表中的“状态变化”都由 Runtime 核验后接受；Agent 和外部服务只产生提议或输入。每一行接受的变化要持久保存依据与版本，不以聊天文本作为恢复源。

## 2. A：正常报销与已有证据复用

输入：申请额 800 元，额度 1,000 元，发票 I1、I2；已有可信且仍有效的 I1 核验记录。

| 时点 | 触发者及输入 | 接受的状态变化 | 执行依据与恢复要求 |
|---|---|---|---|
| A0 | 用户委托正式提交 | 创建 W-A，绑定目标及规范版本 | 保留原请求及已接受范围 |
| A1 | Agent 提议读取业务资料 | 创建获准的读取 Operation | 只在已有读取权限内执行 |
| A2 | HR、票据系统返回记录 | 接受有来源的事实与 I1 证据 | I1 来源、对象和有效期通过验证 |
| A3 | Runtime 求值 | 核验 I1 已满足；I2 待核验；额度检查待完成 | 已有证据可满足义务，不要求重复动作 |
| A4 | Agent 提议 P1 | 激活验证 I2、查重、计算和确认的计划 | 未知条件保留，不提前准入提交 |
| A5 | 指定服务返回结果 | 两票有效、查重通过、额度满足，特别批准不适用 | not_applicable 的依据为 800 ≤ 1,000 |
| A6 | 用户确认单据 D1 摘要 H1 | 记录绑定 H1 的确认 | 若此后内容变化，确认须重评 |
| A7 | Agent 提议正式提交 | 准入并持久化 Operation S1，业务键 K1，内容 H1 | 提交前重验当前版本及授权 |
| A8 | OA 返回受理编号，查询核实 | S1 确认成功，受理证据覆盖 D1/H1 | HTTP 成功码本身不够 |
| A9 | Runtime 执行验收 | W-A closed/succeeded | 记录验收版本、规则与证据集合 |

反例：A3 后 Planner 因 I1 已核验而删除重复调用，可以接受；若同时删掉 I2 的核验要求，Runtime 的义务仍然存在，A7 必须被拒绝。A9 不能声称审批通过或付款完成。

断电检查：A7 后立即重启，系统应恢复 S1 的意图及结果核实工作，不重新生成新的提交业务键。该检查尚待原型执行。

## 3. B：异常发票、部分规划与确认失效

输入：初始金额未确定，发票 I2 核验异常。异常类型允许补充原始证明后重新核验。

| 时点 | 触发者及输入 | 接受的状态变化 | 执行依据与恢复要求 |
|---|---|---|---|
| B0 | 用户委托、初始资料 | 创建 W-B；特别批准条件 unknown | 允许补齐资料，禁止正式提交 |
| B1 | Agent 提议 P1 | 激活读取与核验的部分计划 | 明示核验后再计算、决定后续路径 |
| B2 | 核验服务返回异常 | 接受异常事实；I2 核验义务仍 pending；激活异常处置要求 | 异常处置不能取代有效核验要求 |
| B3 | Agent 提议 P2 | 接受补材料计划，持久注册 Wait U1 | 保留 P1 及已经完成的核验历史 |
| B4 | 没有其他可执行项 | W-B waiting；Agent 会话结束 | 保存所需材料、关联对象、期限和责任人 |
| B5 | 用户补充材料 | 接受材料事件，触发 U1 并恢复求值 | 材料到达不等于核验通过 |
| B6 | 指定服务重新核验通过 | I2 核验及异常处置满足；算出 800 元 | 证据覆盖当前发票集合 |
| B7 | 用户确认 D1/H1 | 当前确认要求满足 | 确认与内容绑定 |
| B8 | 用户增加 I3，总额变为 1,200 元 | 接受 D2/H2；旧确认不覆盖新版本；特别批准适用 | I3 核验及新审批待完成，提交仍受阻 |
| B9 | Agent 提议 P3 | 核验 I3、重做相关查重与计算、特别审批、再次确认 | I1/I2 的有效证据可保留，不要求全量重跑 |
| B10 | 指定批准者和用户完成要求 | 记录覆盖 H2 的特别批准及确认 | 旧 H1 的迟到批准不能代替 H2 |
| B11 | Runtime 准入并核实 OA 受理 | 验收 W-B 成功 | 所有完成范围内条件已解析 |

反例：Agent 直接把“补充了材料”解释为 I2 已通过，不接受。用户始终不补材料时，截止事件按预设策略升级到 needs_attention；不能无限重启 Planner，也不能自动标记成功。

这里暴露出两类独立变化：B3 是执行策略变化；B8 是业务对象变化。它们不一定改变原目标，但都可能改变哪些证据仍然有效。

## 4. C：跨天审批、未知提交结果与重复回调

本次目标明确包含审批通过。前置核验和确认均已满足，单据摘要 H1，审批实例必须覆盖 H1。

| 时点 | 触发者及输入 | 接受的状态变化 | 执行依据与恢复要求 |
|---|---|---|---|
| C0 | Agent 提议创建正式申请 | 持久提交 Operation S1/K1/H1 及可关联等待意图 | 等待关联信息先于可能到来的回调存在 |
| C1 | 外部调用超时 | Attempt A1 传输超时，S1 outcome_unknown | 禁止把它当作确定失败 |
| C2 | OA 已创建申请 X1，但 Runtime 随后重启 | 本地仍保留 S1 和未知结果 | 重启不需要原模型会话 |
| C3 | 恢复任务按 K1 查询 OA | 找到 X1/H1，S1 confirmed_succeeded | 如果查不到但查询可能滞后，继续按未知处理 |
| C4 | Runtime 建立审批等待 | W-C waiting，记录 X1、H1、期限和审批来源 | 未收到批准证据，不能关闭成功 |
| C5 | 三天后 OA 发出批准 E1 | 核验来源、审批权限、X1/H1 后接受证据 | 触发等待，重新求值当前规范与条件 |
| C6 | OA 重复投递 E1 | 去重，不重复触发业务动作 | 不创建第二次申请、不生成第二份验收 |
| C7 | Runtime 验收 | W-C closed/succeeded | 目标是审批通过，不推断付款 |
| C8 | 迟到的旧“审批中”消息 | 保留接收记录，不回退已验证状态 | 依据版本关系，必要时查询权威状态 |

补充故障分支：

| 注入点 | 应有行为 |
|---|---|
| C3 找不到记录，OA 支持有效的幂等重放 | 核实能力与授权仍有效后，用相同 K1/H1 再次尝试 |
| C3 无查询、无幂等能力 | needs_attention，保留未知效果，不自动换键重试 |
| C5 回调先于等待正式激活 | 从持久收件记录关联，不能丢失通知 |
| C5 是拒绝事件 | 按本例终局拒绝规则关闭为 rejected，不能当作技术失败重试审批 |
| C5 批准的是旧摘要 H0 | 记录但不满足 H1 的审批要求 |
| C5 时执行权限已撤销 | 批准证据仍按其有效性评估；任何新动作重新准入 |
| 取消后才收到批准 | 记录外部事实、核实在途效果，不能自动恢复原提交链 |

## 5. 补充边界挑战

| 场景 | 语义预期 | 对应要求 |
|---|---|---|
| 政策新版本发布，但只适用于未来费用 | 保留原适用规则，记录判断依据 | 政策绑定与迁移 |
| 新要求明确适用于全部未提交申请 | 发布 Contract 迁移修订，重评义务与授权 | R2、R3 |
| 用户把目标从提交改成付款到账 | 明确扩展 Contract、权限和完成条件；不能仅加一个计划节点 | R7 |
| 两个 Agent 同时提交基于旧状态的修订 | 仅接受一个版本更新，另一个重新读取 | R5 |
| 两个 Work 同时报销同一发票 | 外部唯一约束拒绝第二次受理，不能只依赖先前查重结果 | 外部一致性边界 |
| 成功关闭后证据被撤销 | 追加纠正并发起关联整改工作，保留原验收历史 | 证据失效与审计 |
| 计划节点全完成，OA 仍未明确受理 | 保持未成功，继续核实或升级 | R4、R7 |

## 6. 推演结论与下一步验证

这些案例在定义层面支持三项区分：业务要求与动作分离、计划与授权分离、逻辑操作与调用尝试分离。它们尚不足以证明需要独立的 Contract 服务或通用 Graph 引擎。

最小原型应运行同一组轨迹，并在每个持久提交点和外部调用前后注入崩溃。检查：状态可以恢复、同一业务操作不被错误重复、旧证据不能证明新对象、未知条件不能通过准入、成功关闭始终有证据。

这一步只需要假 OA、可控时钟、持久存储和可替换 Planner。可先用确定性脚本模拟 Agent 提议，验证 Runtime 能拒绝错误命令，再接入真实 LLM 验证规划能力。原型结果决定下一版语义和协议，而不是反过来迁就本草案。
