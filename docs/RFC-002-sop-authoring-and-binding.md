# RFC-002：SOP 的表达、发布与实例绑定

版本：0.1 · 日期：2026-10-13 · 状态：候选设计，尚未经实现验证

> 实现状态（2026-10-13）：示例规则 E01–E08 已在本地原型的演示策略中体现为可执行检查，判例 T01–T12 的一部分由命名测试镜像；规则卡发布与作者审阅流程（第 6 节）尚未实现。逐项状态见[验证覆盖](verification.md)。

承接 [RFC-001](RFC-001-core-semantics.md) 第 2 节。本文使用同样的原则、假设、暂定决策和开放问题标记；示例规则仅供设计推演。

## 1. 本轮要收敛的结论

**D10：一份 SOP 应提供三种相互关联的视图：业务人员可审阅的规范、Runtime 可判定的约束、Agent 可采用的执行建议。** 三者可以放在同一文件，也可以分开；它们不是三套可以各自修改的业务真相。

原文用于说明意图和追溯依据，经过发布认可的规范表示用于运行判断。若二者存在语义冲突，不能让 Agent 临场选择解释，应阻止相关规范发布；运行中发现冲突时暂停受影响动作并交由规范责任人裁决。

Agent 的自主空间包括如何收集资料、采用哪种认可的证明方式、怎样组织独立工作和何时提出修订。禁止、必要条件、强制顺序及验收条件不在这个自主空间内。

这意味着初版可以使用 Markdown 加结构化规则卡，而不必先设计通用编程语言。文件名叫 SKILL.md 还是 graph.md，不决定其规范效力。

## 2. 先区分五种容易混淆的表述

| 业务表述 | 类型 | 判断方式 | Agent 自由度 |
|---|---|---|---|
| 纳入申请的发票必须有效 | 结果要求 | 当前发票集合是否被有效证据覆盖 | 可引用已有证据或调用认可服务 |
| 提交前必须取得确认 | 动作前置条件与顺序 | 确认覆盖本次内容，且先于提交 | 可安排取得确认的时机，不能后补代替 |
| 不得修改发票原始金额 | 禁止条件 | 拟执行动作是否修改受保护字段 | 可以纠正提取错误，但须保留原件和更正依据 |
| 超额申请须经指定负责人批准 | 条件义务 | 条件是否适用、是否存在匹配批准 | 可补资料或提请审批，不能自行豁免 |
| 建议先并行核验发票和读取额度 | 执行建议 | 不作为硬性准入条件 | 可改顺序、合并或省去已有结果的操作 |

**D11：同一句要求可能产生多个运行检查，但仍保留同一个规范来源 ID。** “提交前确认”既产生待履行要求，也产生提交准入检查；不能复制成两条互不关联、可能版本不一致的规则。

前置条件控制何时可以行动；义务说明还欠什么；顺序约束检查历史。它们有重叠，但不能互相替代。尤其是“最终都做完了”不能证明“按要求的顺序做了”。

## 3. 业务人员审阅的最小规则卡

每条强制规则至少回答以下问题；字段可以由工具辅助填写，但发布者需要审阅其含义。

| 字段 | 要回答的问题 |
|---|---|
| 标识与原文依据 | 这是哪条制度要求？来自什么版本的哪段原文？ |
| 强制性与类型 | 是必须、禁止还是建议？约束状态、动作还是历史？ |
| 适用范围 | 哪些业务类型、组织、对象及时间范围适用？ |
| 触发条件与依赖 | 依赖哪些事实、对象集合和其他判定？ |
| 要求与截止点 | 必须证明什么？最迟在哪个动作或时间之前？ |
| 判断主体与证据 | 谁能判定？什么来源和版本的材料可以接受？ |
| 未知与冲突处理 | 缺信息时阻止什么，允许补充什么，由谁裁决？ |
| 豁免与违规处理 | 是否可豁免，由谁、在什么范围内批准？已违规如何处置？ |
| 生效与迁移 | 新工作和在途工作分别如何适用？ |

可复用的默认值由发布包显式声明，例如“所有强制规则默认不可豁免”。不能靠字段缺失默认为宽松处理。

**D12：所有允许正式提交或成功关闭的判断，都必须明确其量化对象集合。** “所有发票有效”需要绑定当前申请的发票清单及版本。空集合、未加载完的集合和确实没有发票，是三个不同情况。

规则卡不要求为所有业务判断编写代码。诸如“特殊费用是否必要”，可以指定人工裁决，但必须明确裁决者权限、裁决对象、允许的结果以及其证据如何影响后续执行。

## 4. 一个完整的示例 SOP

示例 ID：expense-submit，规范版本：demo-1。目标仅为正式受理，不包含最终审批通过或到账；特别批准是提交前的例外授权，与提交后的普通审批不同。

适用范围：单个员工、单次差旅、人民币费用；必须至少有一张发票。其他范围在本示例中转人工，不由 Agent 推断规则。

规范责任角色：财务制度发布者。金额、差旅信息、员工身份分别来自指定的票据、差旅和 HR 来源；来源冲突转相关责任人裁决。

| ID | 规范要求 | 触发／截止点 | 认可的证明与阻断范围 |
|---|---|---|---|
| E01 | 申请对象集合完整且非空 | 正式提交前 | 用户声明材料范围，并确认具体单据版本；集合未封闭时阻止提交 |
| E02 | 每张纳入申请的发票核验有效 | 对集合中每张发票，提交前 | 指定核验服务的有效记录，可复用仍有效的既有记录 |
| E03 | 不得重复报销 | 正式提交时 | 提交前查重加 OA 原子唯一约束；冲突则不得受理 |
| E04 | 金额与额度计算明确 | 提交前 | 金额明细与额度规则的版本化计算结果；未知阻止提交 |
| E05 | 申请额高于额度时须特别批准 | 超额为 true，提交前 | 指定财务角色对当前单据内容的批准；false 有依据才不适用 |
| E06 | 用户确认最终提交内容 | 提交前 | 身份已核验用户对当前内容摘要的确认 |
| E07 | 不得改写原始票据 | 所有相关写动作 | 工具能力边界及动作参数检查；提取错误通过追加更正解决 |
| E08 | 证明 OA 正式受理当前内容 | 成功关闭前 | OA 申请 ID、受理状态与对应内容；超时保持未知 |

E01 的“完整”是针对用户确认的本次委托范围，不表示系统能证明现实世界没有遗漏费用。新增发票使该范围产生新版本，并重评相关规则。

E03 分为两个时点：预检查结果用于提交前发现问题；原子唯一约束在外部受理时生效。不能要求“已有受理成功证据”作为首次提交的前置条件，也不能把预检查无重复视为跨 Work 并发安全的证明。

示例权限：仅允许读取本次委托相关资料、请求核验、创建草稿、请求特别批准和提交该申请。权限仍须在动作时验证；SOP 的能力列表不授予访问凭据或企业审批权。

示例失败处理：核验异常允许补充材料后再次核验；确认拒绝则等待修改或取消；特别批准被拒绝后允许用户修改申请或取消，但不能不断重发同一内容以寻求不同结果。错误受理或发现违规时转人工处置，不能自行把历史改成合规。

示例等待策略：材料或确认等待 3 个自然日后进入 needs_attention，由申请人负责响应；特别批准等待 3 个自然日后交财务协调人处置。时间从持久等待注册起计算，按 Work 中记录的时区显示。升级不自动撤销已经创建的外部对象。

示例迁移：demo-1 对已绑定 Work 默认继续适用；后续规范若需迁移在途 Work，须显式发布范围与迁移条件。执行权限撤销仍立即影响后续动作准入。

建议流程：并行收集允许读取的资料 → 尽量复用有效证据 → 核验与计算 → 按需特别批准及用户确认 → 提交并核实。本文不要求特别批准和用户确认之间固定先后，只要求二者覆盖提交内容并先于提交。

### E05 的规则卡展开

```text
规则：E05，来源 expense-submit/demo-1 的超额批准条款
类型：强制条件义务 + submit_expense 的准入要求
对象：当前申请内容版本
依赖：申请金额、适用额度、单据摘要、批准者权限记录
触发：申请金额 > 适用额度
true：需要覆盖当前摘要的有效特别批准
false：记录不适用及金额比较依据
unknown：阻止正式提交，允许获准的读取、计算及补资料
conflict：阻止正式提交，交财务规则责任人裁决
证明：指定批准服务记录，结果为批准，对象及权限范围匹配
截止点：正式提交前
豁免：本示例不允许
失效：金额、额度依据、相关内容或批准有效性变化后重新评估
```

这里的文本是审阅表示，不是已实现的 DSL；它足以暴露需要工程绑定的谓词、判断者和证据要求。

## 5. 从规范到一次 Work：绑定，而非临时解释制度

**D13：发布阶段确定规则含义；实例化阶段代入事实与适用版本；运行阶段持续求值。** 三个阶段都允许发现问题，但只有规范发布机制能修改规范含义。

以示例金额 1,200 元、额度 1,000 元、当前内容 H2 为例：

| 阶段 | 输入 | 产物 |
|---|---|---|
| 发布 | E01–E08、证据定义、执行建议、审阅结果 | 不可变发布包及其内容标识 |
| 绑定 | 请求目标、用户身份、业务范围、政策适用日期 | Work Contract 修订 C1，记录选版依据及待补事实 |
| 求值 | 发票集合 V2、金额、额度、H2 | E02 的逐票要求、E05 的批准要求、E06 的确认要求等 |
| 规划 | 尚未满足的要求、允许能力、当前事实 | Agent 提议验证与请求批准的执行策略 |
| 准入 | 提议提交 H2、当前状态、权限和证据 | 允许，或返回明确的未满足规则及原因 |
| 验收 | OA 对 H2 的受理记录及规则评估 | 对该状态版本的成功关闭决定 |

C1 不要求所有事实在创建时已知。规范包和求值范围已确定、金额尚未知时，保留 E05 的未知状态；若连适用规范都无法确定，停留在 establishing，只执行独立获准的初始化动作。

Contract 至少保留：目标及范围、规范包身份、政策绑定依据、权限边界引用、验收范围和修订策略。当前额度、批准记录等动态求值结果放在事实和证据状态中，不因每次新增事实都复制一份 Contract。

仅当目标、规则绑定或其他约定边界变化时产生 Contract 修订；计划修订与事实版本各自演化。这样可避免三个版本号无意义地一起增加。

## 6. 发布前必须证明什么

发布流程候选：业务草稿 → 辅助抽取规则卡 → 消解歧义与工程绑定 → 静态检查及场景回归 → 有权主体认可具体内容 → 发布不可变版本。

认可绑定精确内容标识，之后的任何修改都需要新版本。草稿、Skill 推荐或历史聊天中的建议不能直接成为强制运行规则。

| 检查 | 典型不通过情况 |
|---|---|
| 可追溯 | 一条强制要求找不到制度来源，或原文条款未被覆盖也未说明排除原因 |
| 可判定 | “金额较大需领导审批”，但阈值及领导角色未定义 |
| 对象明确 | “检查全部发票”，但不知道集合来自哪里、是否完整 |
| 截止点明确 | 只写“需要批准”，未说明在提交前还是提交后 |
| 证据明确 | 接受任意文本中的“已批准”，没有来源与对象约束 |
| 权限闭合 | 同一个 Agent 可以自授批准权限或绕过执行边界 |
| 无明显死锁 | A 要求先有 B，B 又要求先有 A，且无初始化路径 |
| 能力可实现 | 声称杜绝重复，却没有唯一约束或等价协调能力 |
| 迁移可解释 | 同时要求锁定旧版本与立即采用新版本，但没有适用范围 |

**H5：初版只支持有限对象集合、显式事实依赖及无递归规则。** 限定表达能力是为了让求值可以终止并形成可解释结果。复杂裁量交指定责任人，不使用任意自然语言递归生成无限义务。

静态检查只能发现已表达规则中的问题，不能自动证明所有企业制度已被完整表达。业务发布者负责范围完整性，场景回归和运行反馈用于持续发现遗漏。

## 7. 审阅用判例：相同规范应得到什么结果

以下是预期判定，不是已执行的自动化测试。

| 判例 | 提交前状态 | 预期结果 |
|---|---|---|
| T01 | 800 ≤ 1,000，核验及确认有效 | E05 不适用；其余准入条件满足才可提交 |
| T02 | 金额未知，尚无特别批准 | E05 unknown，阻止提交；允许补信息 |
| T03 | 1,200 > 1,000，无特别批准 | E05 applicable/pending，阻止提交 |
| T04 | 1,200 > 1,000，当前内容获批准并确认 | E05、E06 满足；继续检查其他条件 |
| T05 | H1 获批准，拟提交 H2 | 旧证据不覆盖 H2，重新评估并阻止提交 |
| T06 | 已有可信发票核验，没有再次调用核验工具 | E02 可以满足；不强制重复调用 |
| T07 | 发票集合为空或未加载完整 | E01 不通过，不能用“所有已知发票有效”放行 |
| T08 | 提交后补了批准 | 记录顺序违规；不能追认为提交当时获准 |
| T09 | Planner 删除 E05 对应步骤 | 不改变 E05 求值；缺批准仍阻止提交 |
| T10 | 前置条件齐备，但外部提交超时 | 结果未知；E08 未满足，不得成功关闭 |
| T11 | 规则来源冲突，Agent 选择较宽松解释 | 不接受该解释作为准入依据，转责任人裁决 |
| T12 | 用户增加一张票，旧票均已核验 | 保留旧票有效证据，检查新票并重评集合、金额、批准及确认 |

T01–T12 可映射到 [参考轨迹](reference-scenarios.md) 的正常、异常与跨天路径，用于以后规范发布的回归集。后续需补充期限、豁免、来源撤销及审批权限历史变化等判例。

## 8. 本轮评审结论与下一步边界

本轮暂定采用“明确业务要求 + 必要程序约束 + 可替换执行建议”的 SOP 模型。Graph 可以呈现建议路径或实例计划，但单独一张 Graph 无法在本设计中代替证据匹配、未知条件和规范发布语义。

保留的开放问题：

1. 业务作者是否能理解并维护规则卡？需要用真实制度进行作者试用。
2. 内容摘要哪些字段参与计算？展示格式变化与业务内容变化需要区分，规则需由对象类型定义。
3. 撤销批准对过去执行的影响如何判断？需要审批发生时权限、提交时有效性与之后撤销原因的明确政策。
4. 多份 SOP 同时适用时如何组合？首版先限制单个主规范包加显式政策依赖，不引入自动合并任意规范的机制。

[RFC-003：Agent 与 Work Runtime 的交互协议](RFC-003-runtime-protocol.md) 据此定义 `propose_action`、`record_evidence`、`revise_plan` 和 `request_completion` 等语义命令的输入、拒绝原因与版本检查。随后用 E01–E08 和 T01–T12 做最小原型，检验规范能否真正约束执行，而非先扩充 DSL 语法。
