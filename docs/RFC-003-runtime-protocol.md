# RFC-003：Agent 与 Work Runtime 的交互协议

版本：0.1 · 日期：2026-10-13 · 状态：候选协议，尚未实现

> 实现状态（2026-10-13）：最小原型已实现并验证第 9 节 P01–P15 中的 14 项（单进程、本地信任、假 OA）；P13（分布式租约）明确延期，不声称分布式恰好一次语义。逐项状态与证据见[验证覆盖](verification.md)。

前置：[核心语义](RFC-001-core-semantics.md)、[SOP 表达与实例绑定](RFC-002-sop-authoring-and-binding.md)。本文定义语义命令、响应、持久提交边界及恢复规则，不确定 HTTP、MCP、消息队列或 SDK 形式。

P 表示原则，D 表示本草案暂定决策，H 表示待验证假设，Q 表示开放问题；均沿用前文含义，不代表已经批准的产品协议。

## 1. 协议的最小闭环

Agent 读取当前 Work，提议计划或具体动作；Runtime 接受可执行意图，负责派发、核实与状态更新；Agent 读取新状态后继续。外部事件和定时器也能推进 Work，不依赖 Agent 在线。

**D14：所有改变业务状态的请求都是命令，不允许客户端直接覆盖 Work 状态或义务状态。** 客户端可以提交证据候选，不能写入 `obligation.satisfied = true`；可以请求完成，不能直接设置 `closed/succeeded`。

命令回执、操作状态和业务验收是三种独立结果：

| 层次 | 回答的问题 | 示例 |
|---|---|---|
| 命令回执 | Runtime 是否持久接受了该请求？ | 动作意图已登记 |
| Operation 状态 | 逻辑业务操作有什么结果？ | OA 提交结果仍未知 |
| Work 状态与证据 | 目标是否可被证明？ | 未取得受理证据，尚未成功 |

`accepted` 绝不等于“外部执行成功”。传输连接断开也不等于 `rejected`。

## 2. 身份、读取与公共信封

### 2.1 身份来自可信连接

调用主体由认证会话、服务身份或经验证的委托链确定。请求正文中的 `actor_id` 只可作为待核对元数据，不能赋权。用户确认和批准的正文同样不能替代真实的主体认证。

Work 访问同时检查租户与对象范围。外部业务键、证据 ID 和事件游标不具有访问授权能力；拒绝响应也不能泄漏无权读取的规则或业务材料。

### 2.2 查询面

| 查询 | 返回内容 |
|---|---|
| `get_work` | 一致快照：状态版本、Contract／Plan 修订、事实引用、义务评估、等待、未决操作、阻断原因 |
| `get_command` | 按命令 ID 查询持久回执；无记录与查不到须按访问权限区分 |
| `get_operation` | 逻辑操作、尝试摘要、外部关联、核实状态及证据引用 |
| `list_events` | 按不透明游标读取获准的变化通知，包含可排序的 Work 序号 |

快照带 `state_version`、`as_of` 和证据观察时间；一致快照不表示外部世界没有随后变化。大对象可以返回不可变版本引用，分页必须固定快照或明确要求客户端重新读取。

快照可包含下一步提示，但提示不是授权令牌。事件通知可以重复；消费端按游标恢复，遇到保留期之外的游标则重新取快照，不能自行跳过缺失事件拼接状态。

### 2.3 改变状态的命令信封

```json
{
  "protocol_version": "draft-0.1",
  "command_id": "cmd-101",
  "work_id": "W-A",
  "expected_state_version": 17,
  "type": "propose_action",
  "payload": {
    "contract_revision": 1,
    "plan_revision": 2,
    "capability": "expense.submit",
    "subject": {"id": "D1", "revision": 3, "digest": "H1"},
    "intent_key": "submit-D1-r3",
    "arguments_ref": "immutable-payload-42",
    "evidence_refs": ["invoice-check-7", "confirmation-9"]
  }
}
```

以上是示意数据，不是最终 JSON Schema。正文参数或不可变参数引用均可；Runtime 计算并记录规范化内容摘要，不信任客户端声称的摘要。摘要算法、对象规范化版本和业务键编码必须在实现协议中固定。

**D15：第一版采用整个 Work 的状态版本比较，优先保证语义清楚。** 任何已接受的业务状态变化递增版本；命令审计、重复收件或未改变业务状态的候选收件不必递增。粒度过粗可能产生无害冲突，后续再按实际并发需求优化。

`create_work` 无现有 Work 版本，使用租户内创建请求键去重。外部事实收件也不要求发送方知道 Work 当前版本，其特殊规则见第 6 节。

## 3. 命令去重与业务操作去重

**D16：命令重发与业务重试分开处理。**

| 标识 | 生命周期 | 用途 |
|---|---|---|
| command_id | 一个具体请求及其不可变内容 | 解决请求超时后重发 |
| intent_key／Operation ID | 一个确定的逻辑业务效果 | 解决不同命令重复提议同一操作 |
| Attempt ID | 一次真实工具调用 | 记录传输、失败及核实 |
| 外部幂等键 | 由适配器协议绑定到逻辑操作 | 防止外部重复效果，受外部系统能力限制 |

命令身份范围为租户、认证主体和 command_id；Work ID、预期版本及完整内容都参与一致性比较。所有重放先检查当前访问权限，再读取回执，不能因去重绕过身份验证。

同命令 ID、相同内容：返回原回执，即使当前 Work 版本已经变化。响应可另外指出当前版本，但不得篡改原决定。同命令 ID、不同内容：返回 `COMMAND_ID_REUSED`。因此去重判断先于首次处理所需的状态版本检查。

被拒绝的请求也保留回执。补齐审批后应重新读取状态，用新 command_id 提出新请求；重发旧命令只能获得旧拒绝。请求超时而不知道结果时，用原 ID 查询或重发相同内容。

业务去重不能只相信 Agent 提供的 intent_key。Runtime 根据已注册能力的语义构造操作身份，例如租户、申请 ID、内容版本及 `submit` 效果，并检查现存操作。相同操作返回关联的 Operation；相同业务键绑定不同内容则拒绝。不同 Work 对同一发票的竞争仍由外部唯一约束等共享机制控制。

命令回执和操作身份至少保留至工作关闭及约定的客户端重试期结束；若压缩历史，保留去重墓碑或拒绝过期身份。不能删除后把旧 command_id 当成全新请求。具体时长是部署策略，必须公布给调用方。

## 4. 命令集合与控制权

| 命令 | 谁可提出 | 关键检查 | 接受的含义 |
|---|---|---|---|
| `create_work` | 获委托的用户／Agent | 创建去重、目标范围、初始化权限 | Work 已建立，可仍处于 establishing |
| `bind_contract` | 获准的初始化协调者 | 已发布规范、适用依据、目标授权 | 激活首次 Contract 绑定；缺事实仍可保留未知 |
| `revise_plan` | Planner | 基线、约束、未决操作、缺口及后续触发器 | 激活新计划；不授予各动作执行权 |
| `propose_action` | 获准的执行者 | 当前版本、对象、准入条件、操作身份 | 持久登记或关联 Operation 及派发意图 |
| `record_evidence` | 有权提交材料的主体 | 来源、对象、内容完整性、收件去重 | 候选材料已入库，尚不等于验证通过 |
| `register_wait` | Planner／协调者 | 等待对象、事件来源、期限、责任人、现有收件 | 建立持久等待，或发现条件已发生并立即求值 |
| `request_completion` | 执行者／协调者 | 当前版本及完整验收条件 | 原子记录验收决定并关闭为 succeeded |
| `request_cancel` | 工作所有者或被委托者 | 身份、版本、在途效果、取消范围 | 标记取消意图并停止新相关派发，未必已关闭 |
| `revise_contract` | 获授权的变更主体 | 新目标／规范依据、所需认可、受影响效果 | 激活新约定或登记待处置变更，不隐式撤销效果 |

批准、确认、豁免、人工裁决通过证据入口进入，但由不同权限的验证者处理。普通 Agent 无权凭命令类型名称将自己变成批准者。

`register_wait` 只登记等待，不自行发送通知或创建外部审批。需要外部请求时，由 `propose_action` 关联等待意图并保证先持久化；请求本身仍有独立准入与结果核实。

Runtime 内部的 `dispatch_operation`、`verify_evidence`、`reconcile_operation`、`expire_wait` 不暴露为普通 Agent 可任意调用的写状态接口。管理员与人工接管也使用明确命令，不能直接编辑业务状态绕过规则。

**H6：暂不增加单独的“恢复原会话”命令。** 工作恢复由持久等待、未决操作和可执行项驱动，Agent 读取当前快照即可参与。

## 5. 回执与拒绝原因

成功回执示例：

```json
{
  "command_id": "cmd-101",
  "decision": "accepted",
  "receipt_id": "receipt-101",
  "observed_state_version": 17,
  "result_state_version": 18,
  "operation_id": "OP-31",
  "operation_status_at_decision": "prepared"
}
```

`received` 表示已经持久收件但尚未形成接受／拒绝决定，适用于异步命令处理；客户端随后查询。服务在可靠收件前不得返回 received。外部材料的 accepted 仅表示材料收件命令完成，其证据验证状态单独返回为 pending_verification 等。

| 原因码 | 含义 | 调用方应如何处理 |
|---|---|---|
| `STATE_VERSION_CONFLICT` | 基于过期状态提出命令 | 读取新状态并重新推理，不自动仅替换版本号 |
| `COMMAND_ID_REUSED` | 同请求身份绑定了不同内容 | 修复调用错误，不重放变体 |
| `CONTRACT_NOT_ACTIVE` | 相关规范与目标尚未绑定 | 完成获准的初始化工作 |
| `CONTRACT_REVISION_MISMATCH` | 提议依赖旧约定 | 读取新约定，重新判断动作 |
| `PLAN_REVISION_MISMATCH` | 依赖的计划已被替换 | 读取新计划，重提仍需要的动作 |
| `APPLICABILITY_UNRESOLVED` | 必须判断的条件未知或冲突 | 获取允许的信息或请求裁决 |
| `REQUIREMENT_UNSATISFIED` | 已适用要求尚未满足 | 按规则补充证明或执行获准动作 |
| `EVIDENCE_SCOPE_MISMATCH` | 证据不覆盖当前对象或版本 | 获取正确证据，不能改写证据对象 |
| `AUTHORITY_DENIED` | 当前主体或动作无权执行 | 转获授权路径，不自动提升权限 |
| `OPERATION_CONTENT_CONFLICT` | 同业务操作身份绑定了不同内容 | 核实已有操作，再提出合法新版本变更 |
| `OUTCOME_UNRESOLVED` | 相关外部效果未核实 | 查询既有 Operation，等待核实或人工处置 |
| `WORK_NOT_ACTIONABLE` | 工作已关闭、取消中或不允许该动作 | 读取工作状态与允许的后续处置 |

拒绝附可访问的规则 ID、对象引用、当前评估、缺少的证明、是否可通过状态变化后重提，以及查询关联操作的引用。不得返回“试一下其他工具绕过”的恢复建议。

鉴权失败、格式错误、限流及临时服务故障属于入口／传输错误；它们不能被解释为业务效果必然未发生。客户端不确定是否已提交时仍按原 command_id 核实。基础设施恢复不能把确定拒绝自动变成允许。

## 6. 证据与外部事件：持久接收，再合并求值

**D17：外部输入不因 Work 版本变化而丢弃，但必须经过来源核验和当前状态合并。**

收件身份至少绑定来源和来源事件 ID；无稳定事件 ID 时，适配器需提供认可的替代去重依据。仅靠任意文本摘要不能区分两个内容相同但实际不同的业务事件。

处理步骤：核验来源及提交权限 → 去重并持久保存输入 → 验证对象、版本、命题和证据资格 → 基于当前状态求值 → 原子提交接受的事实变化、事件与后续工作。合并期间遇到并发更新时重新求值；不能以发送方的旧快照覆盖当前状态。

同来源事件 ID 但不同内容视为冲突，保留安全的收件审计并升级，不覆盖原事件。未能关联 Work 的合法消息进入有期限的隔离收件区，等待核实；不能仅凭外部正文提供的 work_id 跨租户关联。

迟到批准可以成为某个旧版本的有效证据，但不能因此满足新版本的要求。已关闭工作仍可记录纠正线索，并按政策建立整改工作，不能由收件处理器自动复活。

只收件成功不改变义务满足状态。验证者输出应包含命题、对象、结果、依据、验证者身份与规则版本；必要时记录事件发生时与使用时的权限判断，避免把“当前有权”误当成“当时有权”。

## 7. 从准入到派发的持久边界

**D18：接受动作时，至少原子持久化命令回执、Operation 身份、业务状态变化及派发意图。** 外部工具调用发生在该提交之后。实现可以采用事务发件箱或其他等价机制，本 RFC 不选型。

派发器取得有期限的执行权，并在调用前检查对象版本、取消情况、相关证据和授权仍然有效。若条件不再成立，Operation 保留 prepared，但派发状态置为 held，附阻断原因；若旧计划或对象已明确废弃，则派发状态为 cancelled，且保留 never_dispatched 依据。以上不伪造外部 confirmed_failed。

Operation 的业务结果状态与派发调度状态分别存储。首次接受回执仍为 accepted，后续 held／cancelled 状态通过查询和事件呈现；接受过的命令不追溯改为拒绝。

派发前持久登记 Attempt 和“可能已经调用”的边界。进程在边界附近崩溃时，按可能已发生效果处理，不能因为没有响应记录而判断未调用。

派发租约本身不能保证外部恰好一次：旧执行者失联后可能仍在调用。接管者优先核实或用外部有效幂等语义重放；外部不支持时进入人工核实。栅栏标识只有被外部服务识别和强制检查时，才能阻止旧执行者的写入。

Work 状态更新、证据采纳及依赖重评必须保持一致。未完成重评的状态不能被用于放行相关动作；实现可在同一事务求值，或显式保留 evaluation_pending 阻断状态。

## 8. 一段端到端消息轨迹

下例使用 RFC-002 的 E05 特别批准、E06 确认和 E08 正式受理。其他前置条件假设已经满足。所有版本号仅作示例。

| 时点 | 请求／事件 | 结果与持久状态 |
|---|---|---|
| M0 | `get_work(W-B)` | v20，H2，金额 1,200，额度 1,000，E05 pending |
| M1 | cmd-A：propose_action 提交 H2，基线 v20 | rejected：REQUIREMENT_UNSATISFIED，指向 E05；业务状态仍 v20 |
| M2 | cmd-B：register_wait，基线 v20 | 等待审批来源及 H2；接受后 v21。审批请求已由先前获准操作建立 |
| M3 | 指定审批系统上传批准 E1 | 持久收件后验证；E05 satisfied，触发等待，v22 |
| M4 | 用户对 H2 的确认经验证采纳 | E06 satisfied，v23 |
| M5 | Agent 重发 cmd-A 的原始内容 | 返回 M1 原拒绝，不因现在已批准而重新解释 |
| M6 | 读取 v23；cmd-C 提议提交 H2 | accepted，OP-7/prepared，v24；响应在网络中丢失 |
| M7 | Agent 重发完全相同的 cmd-C | 返回原回执及 OP-7，不创建第二个操作 |
| M8 | 派发 OP-7，OA 超时 | Attempt 结果超时；OP-7 outcome_unknown；推进状态版本 |
| M9 | Runtime 重启，按业务键查询 | 查得 OA 已受理 H2；采纳受理证据，OP-7 confirmed_succeeded |
| M10 | 读取当前 vN；cmd-D：request_completion，基线 vN | 全部验收通过，原子记录验收及关闭 vN+1 |
| M11 | OA 重投同来源事件 E1 | 去重，无新业务副作用，不复活工作 |

M6 之后即使 Agent 用新 command_id 再次提议同一逻辑提交，Runtime 仍应关联 OP-7。请求去重和业务去重缺一不可。

若 M8 前单据改成 H3，派发前检查应阻断尚未派发的 H2 操作；若修改发生在外部调用已开始后，不能保证撤销 H2，必须核实旧操作并按修订规则处理真实效果。

## 9. 故障与并发验收矩阵

以下是待实现的协议测试规格，尚未执行。（2026-10-13 更新：P01–P15 的实际通过/延期状态与证据测试见[验证覆盖](verification.md)。）

| ID | 注入条件 | 必须观察到的结果 | 对应前文 |
|---|---|---|---|
| P01 | 相同命令并发到达 | 一个持久决定，其余重放同一回执 | R4、命令身份 |
| P02 | 相同命令 ID 改参数 | 拒绝 ID 复用，无第二次意图 | E06、T05 |
| P03 | 两个命令基于相同版本修改计划 | 只接受一个冲突修改，另一个版本冲突 | R2、R5 |
| P04 | 回执丢失后重发 | 返回已有 Operation，无新效果 | R4、T10 |
| P05 | 用新命令 ID 重提相同提交 | 关联已有 Operation，不能逃避业务去重 | E03 |
| P06 | 意图提交后、调用前崩溃 | 可恢复派发；临界区不明时先核实 | R1、R4 |
| P07 | 外部成功、本地记结果前崩溃 | 查回同一外部记录；不换业务键创建 | R1、T10 |
| P08 | 批准比等待注册更早到达 | 已存证据触发求值，无永久丢唤醒 | R1、R6 |
| P09 | 旧版本批准及重复回调 | 留历史或去重，不满足新内容 | R5、R6、T05 |
| P10 | 计划修订删掉批准步骤 | 义务仍在，提交仍拒绝 | R2、T09 |
| P11 | 成功回执后、派发前撤销授权 | held 并记录原因，不产生新调用 | P2、Authority |
| P12 | request_completion 缺少受理证据 | 拒绝关闭，保留未决效果与要求 | R7、T10 |
| P13 | Worker 租约过期但旧调用仍在运行 | 核实或安全幂等接管，无盲目重复调用 | R4 |
| P14 | 金额未知／发票清单未封闭 | 阻断提交，允许获准的补信息动作 | R3、T02、T07 |
| P15 | 证据采纳后求值进程崩溃 | 恢复重评；重评未完成时不得准入相关动作 | R1、R3 |

测试必须检查副作用次数、实际外部对象、持久回执和验收证据，不能只检查某个函数返回 accepted。无幂等且无查询的适配器应明确得到 needs_attention，而不是期望不存在的自动恢复保证。

## 10. 原型范围与尚未解决的问题

最小原型覆盖 create_work、首次绑定、读取、计划修订、动作提议、材料验证、等待、结果核实和完成请求；使用单租户、单进程协调、持久存储与假 OA。命令重复、进程重启及故障点仍需实际模拟。分布式租约验证作为单独阶段，不能用单进程测试声称 P13 的分布式性质已验证。

第一版可以使用固定发布包与确定性 Planner，先验证 E01–E08、T01–T12 和 P01–P15。真实 LLM 接入用于检验提议质量和恢复上下文是否足够，不承担替 Runtime 修复状态的职责。

仍需决定：

1. 协议格式、内容规范化及去重数据保留策略。
2. 外部能力如何声明幂等有效期、查询一致性、唯一约束与结果证明方式。
3. Contract 修订、取消及人工接管的完整确认和责任转移协议；原型未实现时必须明确拒绝不支持的命令，不能假装完成。
4. 大 Work 的并发粒度及分页一致性是否需要超出当前全 Work 版本方案。

下一步应实现上述有限范围的参考运行时，并报告每个验收项实际通过、失败或未覆盖。暂不扩展成多服务架构或完整企业规范编辑平台。
