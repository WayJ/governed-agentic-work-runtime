# S8 Task3 revocation demo and installed entry points — scoped implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans task-by-task. Coordinator owns dispatch; no extra workers.

**Goal:** A real, reproducible, no-credentials `revocation-demo` on fresh stores for both policy families, runnable as `python3 -m work_runtime revocation-demo` and installed `work-runtime revocation-demo`, with an installed-verifier stage that proves counts/states/fingerprints/operation keys independently of printed text.

**Architecture:** One new demo module drives the unchanged Runtime/public command protocol (accepted core `a1680a7`, carrier `41583e2`) exactly as `intervention_demo.py` does — three scenarios, each owning a fresh store pair, every printed count asserted by the module itself. The CLI gains one subcommand; `scripts/verify_install.py` gains two stages (module + console) that re-verify the demo's stores directly through SQLite with the standard library only.

**Tech Stack:** Python>=3.9 stdlib/unittest, SQLite, zero runtime dependencies.

**Spec:** [Ratified S8 design D33–D37](../specs/2026-10-14-s8-evidence-revocation-design.md), [S8 revocation plan](2026-10-14-s8-revocation.md) Task3, [S8 core integration review](../../../.agents/notes/2026-10-14-S8-core-integration-review.md) "Carrier and public interfaces" section, [sprint](../sprints/2026-10-14-S8-plan.md).

## Review Focus

- **Fabricated evidence states via SQL** — the demo must build every state through public commands/adapters; the tests read SQLite only to assert what the public path produced. Pinned by every demo test asserting rows the real commands wrote (Task 1).
- **Counts that don't match the external stores** — every printed number must be backed by an actual adapter count; the final summary line is asserted against all three external stores. Pinned by `test_each_external_store_is_counted_independently` and the repeatable-runs test (Task 1).
- **Closed-work correction silently rewriting history** — completion must stay byte-identical after the closed-store revoke; pinned by comparing the completion JSON read before and after the revoke through public `get_work` (Task 1, publish scenario test).
- **Installer proof that trusts stdout** — `verify_install` must assert states/fingerprints/business keys read from the demo's databases, not exit codes or printed lines; pinned by helper tests that tamper with a real store and require rejection (Task 3).
- **Claims of console coverage never run** — only add console-stage claims for `revocation-demo`, which the script actually executes; do not touch the publish-demo wording. Pinned by doc-sync review in Task 5 and the real full-script run recorded in the report.

**Scenario A — expense, store `hold/`, work `hold` (predispatch hold + replacement readmission):**
1. `initialize` + `prerequisites` (approval `evt-hold-approval` verified) → propose → prepared intent (operation id).
2. finance (current approval source, holds `evidence.revoke`) revokes `{source:"finance", event_id:"evt-hold-approval", reason:"withdrawn by finance"}` version-bound → accepted receipt `evidence_status:"revoked"`, `prior_status:"verified"`; E05 → pending.
3. re-propose → rejected `REQUIREMENT_UNSATISFIED` with blocker `E05:EXP-001`.
4. dispatch → `held`/`REQUIREMENT_UNSATISFIED`, `attempts == []`, OA receipts table 0, accepted 0.
5. replay the same revoke command id → stored receipt verbatim, `EvidenceRevoked` event count still 1.
6. resend the same approval source event under a NEW `record_evidence` command → same `evidence_id`, `evidence_status:"revoked"`, no new row.
7. replacement approval `evt-hold-approval-2` (new event id) → `verify_pending` → E05 satisfied → re-propose → SAME `operation_id` → dispatch → `confirmed_succeeded`; accepted applications in this store: 1.

**Scenario B — expense, store `uncertain/`, work `uncertain` (retained external effect exactly once):**
1. prerequisites + approval → propose → prepared.
2. dispatch with `FakeOA(timeout_after_commit=True)` → `outcome_unknown`; OA store: accepted 1 (effect exists though the response was lost).
3. finance revokes the approval → E05 pending (current authority withdrawn mid-flight).
4. reconcile the ORIGINAL business key → `confirmed_succeeded`, `external_id` recovered (`OA-…`), `attempts == 1`, nothing resent; accepted still 1; acceptance recorded as verified business evidence under the operation id.
5. root (admin) revokes the confirmed acceptance proof `{source:"oa", event_id:<operation_id>}` → E08 pending.
6. re-propose → SAME operation returned with `operation_status_at_decision:"confirmed_succeeded"` (E08 is not an admission blocker) — a confirmed effect never re-executes to regenerate a revoked proof; dispatch again → confirmed, no new attempt, accepted still 1.
7. `request_completion` → rejected `REQUIREMENT_UNSATISFIED` (blockers E05 revoked approval + E08 revoked acceptance); accepted applications in this store: 1; effects reversed: 0.

**Scenario C — publishing, store `publish/`, work `publish` (hold, readmission, closed correction):**
1. reviewer approval `evt-pub-approval` + author confirmation recorded → verified → propose → prepared.
2. reviewer (current source + `evidence.revoke`) revokes the approval → C02 pending.
3. dispatch → `held`/`REQUIREMENT_UNSATISFIED`, attempts [], `published_count() == 0`.
4. replacement approval `evt-pub-approval-2` → verify → re-propose → SAME operation id → dispatch → `confirmed_succeeded`; published artifacts: 1.
5. `request_completion` → accepted → `closed/succeeded`; completion cites the verified acceptance evidence id.
6. root (admin) revokes the publisher's acceptance proof `{source:"publisher", event_id:<operation_id>}` → work stays `closed/succeeded`, completion byte-identical, C04 → pending, `EvidenceRevoked` event has `work_was_closed` and `completion_cites_evidence` true.
7. resend the original reviewer approval event under a NEW command → same `evidence_id`, `evidence_status:"revoked"`; published artifacts still 1; effects reversed: 0.

Final print: the exact final line above plus the three inspect lines (`hold`, `uncertain` plain expense; `publish` with `--policy content-publish`).
