# S8 evidence revocation — independent source-grounded design review

Date 2026-10-14. Reviewer: dispatched planning reviewer (design-only, no implementation). Checkout `s8-evidence-plan` at `57be566`; baseline published main `48c01fd`. Inputs read: [design](../../docs/superpowers/specs/2026-10-14-s8-evidence-revocation-design.md), [E8 roadmap](../../docs/superpowers/roadmaps/2026-10-14-evidence-revocation.md), [recon](2026-10-14-next-core-recon.md), [RFC-001](../../docs/RFC-001-core-semantics.md) (§4.2, §5, D8, §8), [RFC-003](../../docs/RFC-003-runtime-protocol.md), [runtime-boundaries](../../docs/runtime-boundaries.md), [verification](../../docs/verification.md), and the actual `runtime.py`, `policy.py`, `publishing.py`, `ingress.py`, `inspection.py`, GUI assets and the relevant tests. One bounded non-product probe was run from `/tmp` (§3, D-1) to confirm a latent closed-work defect that Q2 must disposition.

## 1. Verdict

The design is implementable on the current runtime with **no schema change** (schema stays `1`; revocation is a status flip inside `evidence.body` plus new command/event kinds), no new dependencies, and no write UI. Both policy families need **zero policy-code changes**: `ExpensePolicy.evaluate` and `PublishingPolicy.evaluate` select proofs by `status == "verified"` (`policy.py:89`, `publishing.py:63`), so a new terminal `revoked` status stops satisfying requirements by construction, and migration/verify_pending already skip non-verified/non-pending proofs. The four open questions are real but each has a recommendation below that stays inside existing machinery. Two genuine pre-existing defects/edges (D-1, D-3) were found during grounding and must be dispositioned by the master **before** interfaces are pinned, because the recommended Q2/Q3 designs touch the same lines.

## 2. Grounding facts the design can rely on

Numbered facts with exact references; every recommendation below builds only on these.

1. **Command envelope/dedup.** `command()` fingerprints `(work_id, kind, payload, expected_version)` under `(actor, command_id)`, replays return the stored receipt verbatim, and a reused id with different content is `COMMAND_ID_REUSED` (`runtime.py:246-260`). `expected_version` is required for every kind except `create_work`/`record_evidence` (`runtime.py:246-247`) — a new revoke kind is version-bound by construction.
2. **Replay rechecks current authority — but only for kinds it knows.** `_replay_denial` re-evaluates authority per kind (`runtime.py:284-313`); unknown kinds fall through `ok = True` (`runtime.py:311-312`). A new revoke kind **must** add an explicit branch or its accepted receipts replay without any authority recheck — directly contradicting the design's replay-time authority requirement.
3. **Closed-work routing.** The closed guard `WORK_NOT_ACTIONABLE` runs in `command()` for all kinds except `record_evidence` (`runtime.py:269-274`). Late evidence on a closed work is accepted today and provably does not reopen it or alter the completion snapshot (`test_late_event_does_not_reopen_closed_work`, `tests/test_runtime.py:300-310`). Any revoke-on-closed-work semantics needs an explicit carve-out here (like `record_evidence`) — it cannot go through `_apply`.
4. **Evidence identity is globally `(source, event_id)` with content fingerprint.** `_receive` inserts under `PRIMARY KEY(source, event_id)`; same fingerprint resends return the same `evidence_id`; different content is `SOURCE_EVENT_CONFLICT`; cross-work reuse of an event id conflicts because the fingerprint embeds `work_id` (`runtime.py:642-664`; pinned by `test_event_id_reused_across_works_is_source_event_conflict`, `tests/test_ingress.py:238-245`). **Row deletion would break permanence** — a deleted row would let a resend recreate a fresh `pending_verification` candidate. Revocation must be a body-status UPDATE, never a DELETE.
5. **Intake does not re-evaluate; verification and migration do.** `_receive` never calls `_save`, so requirements only move when `verify_pending` (pending→verified/invalid under the *current* configured source, atomically, `runtime.py:666-689`) or `migrate_policy` (verified→verified/invalid, `runtime.py:563-575`) runs. Both run on closed works too (`verify_pending` has no closed check; the late-event test proves it is safe for bound works). Migration touches only `status == "verified"` proofs (`runtime.py:565`) and `verify_pending` only `pending_verification` (`runtime.py:673`) — a terminal `revoked` status is skipped by both, so restart/migration cannot revive it structurally.
6. **Dispatch is the single revalidation point for prepared intents.** `dispatch()` re-runs blockers and authority inside one transaction and holds (`dispatch_state="held"`, reason `REQUIREMENT_UNSATISFIED`/`AUTHORITY_DENIED`) with zero attempts and zero external calls (`runtime.py:736-744`); `recover()` dispatches `prepared/ready` intents through the same checks (`runtime.py:830-844`). So "cannot dispatch on stale revoked approval" needs **no new mechanism** — it needs the revoke handler to call `_save` so `_evaluate` recomputes requirements, plus named tests.
7. **Accepted-kind proofs are runtime-written exactly once.** `_resolve` INSERTs a verified `accepted` proof with `event_id = operation id` under the policy's accepted source, only at first confirmation; confirmed operations never re-resolve (`runtime.py:800-828`, early return `:803-804`; `reconcile` early-returns for confirmed ops `runtime.py:778-779`). Signed ingress can never supply kind `accepted` (`ingress.py:25,177-178`); only trusted-local `record_evidence` by the accepted source could collide with a future op-id event id (see D-4).
8. **Completion and cancellation closure are immutable snapshots.** `request_completion` records `completion.evidence` = verified proof ids at close (`runtime.py:409-414`); `finalize_cancel` records acknowledged succeeded operations with external ids and every disposition (`runtime.py:491-500`). Nothing rewrites them afterwards.
9. **Waits.** `_evaluate` triggers waiting waits when their requirement is satisfied/not_applicable, never demotes triggered waits, and skips cancelled waits terminally (`runtime.py:189-195`); `expire_waits` flips waiting→expired and sets `needs_attention` (`runtime.py:691-704`). Cancelled waits can never re-trigger (`runtime.py:190-191`). There is no wait "reset" anywhere.
10. **Inspection/GUI are data-driven over stored statuses.** `ReadOnlyInspector.summary` counts `evidence_statuses` and `event_types` generically (`inspection.py:190-200`); `work_detail` exposes each proof's stored `status` plus `completion_raw` (`inspection.py:299-315`). The GUI renders status text verbatim in chips (`app.js:626`) but colors only enumerated statuses (`app.css:231-235`) and the summary tile counts only `pending_verification` evidence (`app.js:286-287`).
11. **Re-admission machinery exists.** A `prepared` op left `cancelled`/`held` is re-admitted by a fresh `propose_action` once checks pass (`OperationReadmitted`, `runtime.py:623-629`); business-key dedup returns the existing operation for the same logical effect (`runtime.py:617-631`).

## 3. Pre-existing defects/edges found during grounding (master must disposition)

- **D-1 (material, confirmed by probe): `finalize_cancel` on an unbound work never persists `status="closed"`.** `_evaluate`'s unbound branch resets status to `establishing` unconditionally (`runtime.py:184-186`), and it runs *inside* `_save` *after* the handler set `closed` (`runtime.py:491-500` → `:200-206`). Probe (non-product, `/tmp/s8-probe/probe_closed_unbound.py`): create unbound work → record pending evidence → request_cancel → finalize accepted → stored status `establishing`, outcome `cancelled`, completion snapshot present. Consequences today: the work is counted open by inspection/GUI, `expire_waits`' closed guard (`runtime.py:694`) does not protect it, and `command()`'s closed guard (`runtime.py:271`) does not gate it (only the sticky `cancellation` intent does). This contradicts [runtime-boundaries](../../docs/runtime-boundaries.md) ("Accepted finalize closes the work as cancelled"). Any S8 revoke-on-closed-work path keyed on `status == "closed"` inherits this hole. Recommended: fix the guard (`if not work["contract"]: if work["status"] != "closed": work["status"] = "establishing"; return`) with its own RED/GREEN in S8, or at minimum restrict/track it — S8 adds new `_save`-on-closed paths and should not build on a broken invariant.
- **D-2 (adjacent): unbound-closed status flip is also reachable via `verify_pending`/`recover()`** — same root cause as D-1; any supervisor loop calling `recover()` on a store containing such a work writes events to a finalized work. Fixed by the same one-line guard.
- **D-3 (test-gap that becomes live code in S8): the dispatch-held `REQUIREMENT_UNSATISFIED` path is currently unreachable and untested.** The only tested hold reasons are `ADAPTER_ACTION_UNSUPPORTED` (`tests/test_adapter_contract.py:340-355`) and `AUTHORITY_DENIED` (P11). Today no mechanism makes a requirement unsatisfied *without also cancelling* prepared intents (document/plan revision and migration all cancel; verification only moves pending→verified/invalid, never verified→unsatisfied). Revocation between prepare and dispatch makes `runtime.py:736-744` live for the first time — it must get named tests (held, zero attempts, zero external calls, `DispatchHeld` event) rather than being assumed from P11.
- **D-4 (exotic, trusted-local only): a trusted-local `record_evidence` of kind `accepted` with `event_id` equal to a not-yet-confirmed operation id** makes `_resolve`'s later INSERT raise `IntegrityError` on every reconcile attempt (rollback loop; op stays `dispatched`). Signed ingress cannot produce this (reserved kind); it requires the accepted source itself to misuse direct runtime access. Revocation never deletes rows so it neither causes nor fixes this. Recommend: record as a known limitation or reject `record_evidence` whose `event_id` collides with an operation id — master's call, low priority, but it should be a *stated* edge, not a surprise.

## 4. The four ratification questions

### Q1 — Exact command payload, authority, receipt/event fields

**Recommended interface** (fits the [interventions](../../docs/interventions.md) command table and `_replay_denial` routing):

- Kind `revoke_evidence`; payload exactly `{"source": str, "event_id": str, "reason": str}`, all nonempty strings (malformed → `CommandError`, house style of `request_cancel`/`migrate_policy`). `source` is explicit so the admin path and replay-time authority recheck are recomputable without deriving from the actor.
- `expected_version` required (it is not `create_work`/`record_evidence`, so `runtime.py:246-247` enforces it) → stale use is `STATE_VERSION_CONFLICT` before anything else, satisfying "version-bound … stale use atomically".
- Authority predicate: **current configured source for the stored proof's kind holding a new `evidence.revoke` grant, OR a `work.intervene` administrator** — `actor == policy.evidence_sources[proof.kind] and "evidence.revoke" in grants[actor]` or `self._is_admin(actor)`. Rationale: the issuing-source half mirrors `record_evidence`'s predicate (`runtime.py:649-651`, replay branch `:297-300`) so authority travels with the *current* policy configuration; the admin half mirrors `migrate_policy` (`runtime.py:532-533`) for corrections the configured source cannot make (including accepted-receipt revocations after external effects). A distinct `evidence.revoke` grant (instead of reusing `evidence.write`) keeps "may submit candidates" and "may revoke" separable; grants are configuration strings, so this costs nothing.
  - **Retired source after migration falls out precisely:** the predicate reads the work's *pinned* policy mapping (`_policy_for`), so a source removed from the target version's `evidence_sources` loses revoke rights (and cannot record new evidence either); the newly configured source and admins gain them. Note migration itself already revalidated every surviving `verified` proof under the target's sources (`runtime.py:564-571`), so this is coherent, not a loophole.
- Validation order inside the single transaction: authority → row lookup by `(source, event_id)` → missing = `EVIDENCE_UNKNOWN`; row's `work_id != command work_id` = `EVIDENCE_SCOPE_MISMATCH` (reuse of the existing RFC-003 vocabulary); status `revoked` already = `EVIDENCE_ALREADY_REVOKED` (house style: `CANCELLATION_ALREADY_REQUESTED`); status `invalid` = `EVIDENCE_NOT_REVOKABLE` (nothing current to revoke; never fabricate revocation history for a proof that never verified). Revocable statuses: `pending_verification` and `verified` — this delivers "pending proof revoked before verify_pending cannot later become verified" because `verify_pending` adopts only `pending_verification` (`runtime.py:673`).
- Effect: `UPDATE evidence SET body=?` flipping only `status` to `"revoked"` (**never DELETE** — permanence depends on fact 4), then `_save(db, work, "EvidenceRevoked", details)` so requirements recompute atomically. Event details: `{actor, evidence_id, source, event_id, kind, prior_status, reason, affected_requirements: [{id, from: "satisfied", to: "pending"}], wait_dispositions: [{wait_id, status, disposition: "unchanged"}]}`. `affected_requirements`/`wait_dispositions` are computed by diffing requirements and listing related waits — they make Q2/Q3 explicitness auditable from the event log without mutating waits.
- Receipt: `{"decision": "accepted", "result_state_version": N, "evidence_id": …, "evidence_status": "revoked", "prior_status": …}`. Original command/source-event fingerprints and all prior receipts are untouched (commands row is only the new one).
- **`_replay_denial` must gain a `revoke_evidence` branch** implementing the identical predicate against the current grants/policy/ownership (fact 2). This is the one compatibility edge that silently violates the design if missed.
- Routing/carve-outs: handle `revoke_evidence` beside `record_evidence` in `command()` (`runtime.py:269-270`) — i.e. allowed on closed works (Q2) and during an active cancellation intent (evidence lifecycle keeps running under cancellation, [runtime-boundaries](../../docs/runtime-boundaries.md)); rejected `CONTRACT_NOT_ACTIVE` for unbound works only if the master prefers avoiding D-1 that way (see Q2). Cancellation-active is a genuine sub-decision: allowing it is consistent with "evidence intake/verifier keep running"; rejecting it matches management mutations. Recommendation: allow.

**Alternative options, honestly weighted:** source-only authority (no admin) is simpler but cannot express "the business revokes an OA acceptance the OA source won't retract" — the retained-effect accountability case the roadmap explicitly owes; admin-only is simplest but makes every routine source correction an admin action and diverges furthest from `record_evidence` symmetry. The union costs one extra predicate clause and one replay branch.

### Q2 — Closed-work correction without erasing historical completion

**Recommendation:** allow `revoke_evidence` on **bound** closed works via the Q1 carve-out. The stored effect is: proof status → `revoked`, `EvidenceRevoked` event appended, `state_version` bumps (precedent: `verify_pending` already bumps closed works' version — fact 5), **`status` stays `closed`, `outcome` stays `succeeded`/`cancelled`, and the `completion` snapshot stays byte-identical** (guarded today by `_evaluate`'s `status != "closed"` branch, `runtime.py:187`, and proven for late evidence by `test_late_event_does_not_reopen_closed_work`). Requirements recompute and will show the affected rule `pending` — which is exactly the required distinction: *current validity* (requirements + proof status) vs *the original closure decision* (`completion` snapshot) vs *retained effects* (operation rows keep `confirmed_succeeded` and `external_id` untouched). No implicit reopen, no history edit, no new "reopened" status.

- **Do not add a work-level annotation field.** "Audit attention" is derivable from real stored fields: `completion.evidence` ids ∩ proofs with `status == "revoked"`. If the UI wants a visible marker it must be derived at read time, not stored (a stored flag would be a second, drift-prone copy of the proof status).
- **D-1 must be dispositioned first** (§3): with the one-line `_evaluate` closed guard fixed, the above is safe for all works; alternatively restrict revoke to bound works and reject unbound with `CONTRACT_NOT_ACTIVE` (mirroring `_apply` `runtime.py:367-368`), leaving D-1 as tracked debt. Recommendation: fix the guard — S8 is adding `_save`-on-closed paths, so the invariant should be made true, with a dedicated RED/GREEN proving finalize-then-verify keeps `closed`.
- **Do not** set `needs_attention` on revocation: it is sticky until close ([runtime-boundaries](../../docs/runtime-boundaries.md)) and would be a one-way door for what is usually a routine correction; the recomputed `pending` requirements plus the event are the truthful signal. (Sub-decision; flag for master.)

### Q3 — Waits and prepared intents under revoked proof

**Recommendation: revoke mutates no waits and no operations; correctness comes from existing revalidation points, and explicitness comes from the event.**

- Waiting waits whose requirement went satisfied→pending stay `waiting` — still semantically correct (they wait for satisfaction); their original deadline still governs (`expire_waits` will expire them; **no deadline reset is claimed**).
- Triggered waits stay `triggered` — the trigger was a real historical event; `_evaluate` never demotes (fact 9). If the business needs to re-await, it registers a *new* wait (`register_wait` works because the recomputed requirements include the now-pending rule). Cancelled waits stay cancelled — terminal, no resurrection (`runtime.py:190-191`). All of this is recorded per-wait in `EvidenceRevoked.wait_dispositions` (Q1), which is what makes the disposition *explicit* rather than implied.
- Prepared intents: no eager mutation. The next `dispatch()`/`recover()` holds with `REQUIREMENT_UNSATISFIED`, zero attempts, zero external calls (fact 6) — this is D-3 becoming live and needs its own named tests in both families. Re-admission after replacement evidence verifies rides the existing `OperationReadmitted` path (fact 11). An eager `held` write at revoke time would be redundant state (blockers are always recomputed) and would add a second transition to test for no behavioral gain.
- In-flight/uncertain operations: revocation does not fence them (attempt persisted before the external call, `runtime.py:754-757`); they reconcile/confirm normally and `_resolve` writes a **new** accepted proof under a new event id (the operation id) — no collision with the revoked row (fact 7, and revoke never deletes). "Zero new external calls before dispatch; exactly one retained effect after ambiguous acceptance" is exactly the existing dispatch/reconcile contract; tests must count external store effects, not runtime return values.
- Revoking the accepted proof of a *confirmed* operation never touches the operation: `confirmed_succeeded`, attempts and `external_id` are retained — revocation is not compensation and must not claim to be.

### Q4 — Dedup resend vs fresh replacement proof; permanence

**Permanence is structural — ratify the invariants rather than add machinery:**

1. Revocation is a body-status flip; rows are never deleted (fact 4). Therefore a same-source-event resend hits the `(source, event_id)` dedup and can never create a fresh candidate; different content is `SOURCE_EVENT_CONFLICT`. The same candidate can never be re-verified: `verify_pending` and migration skip non-pending/non-verified statuses (fact 5). Restart changes nothing (statuses are durable; `recover()` only runs the same checks).
2. **Resend receipt should stop being status-silent.** Today the dedup path returns `{"decision": "accepted", "evidence_id": …}` with no status (`runtime.py:656-658`) — a resend of a revoked (or invalid) proof looks identical to a live one. Recommend adding the current `evidence_status` to *new-command* resend receipts (one line, additive; existing tests assert keys, not exact dicts — `tests/test_ingress.py:227-235`). Original-command replays keep returning the original receipt verbatim, unchanged.
3. **Fresh replacement proof = a new source event id** carrying the currently required content (policies bind `data.digest == current document_digest`, `policy.py:91-93`, `publishing.py:65-68`), from the currently configured source. For the `accepted` kind specifically, the runtime must **never synthesize a replacement**: a confirmed operation is terminal and never re-resolves, so replacement acceptance is either (a) the accepted source issuing a new acceptance event, or (b) a new operation under a new business key (new document revision/digest) whose confirmation writes a new proof. State this in docs; a "re-run the same operation to regenerate its proof" path would be a fabricated effect count.
4. Original request fingerprints, stored receipts and the historical accepted receipt all remain untouched — the revoke command adds rows; it edits none.

## 5. Ranked questions for master ratification

Ranked by decision leverage (each blocks the next):

1. **Q1 authority + payload + codes + replay branch** (§4 Q1) — everything else hangs off this interface; the `_replay_denial` branch and the `command()` carve-out placement are hard compatibility edges.
2. **Q2 closed-work representation + D-1 disposition** (§3, §4 Q2) — must be settled *with* the D-1 fix decision; building revoke-on-closed on the current unbound-finalize behavior would bake in a broken invariant.
3. **Q4 permanence invariants + resend status + replacement definition** (§4 Q4) — mostly ratifying what is structurally true, plus the one-line resend receipt change and the explicit no-synthetic-replacement rule.
4. **Q3 waits/prepared non-mutation + event-recorded dispositions** (§4 Q3) — smallest code surface, but the D-3 test gap means "held with zero external calls" must be proven, not assumed; do not shrink it just because the mechanism already exists.

Secondary sub-decisions surfaced (each needs a one-line master choice, none blocks the others): new `evidence.revoke` grant vs reuse `evidence.write`; allow revoke during active cancellation (recommended: allow); allow on unbound works (recommended: no, `CONTRACT_NOT_ACTIVE`, plus the D-1 guard fix regardless); `needs_attention` on revoke (recommended: no); split codes `EVIDENCE_ALREADY_REVOKED`/`EVIDENCE_NOT_REVOKABLE` vs one code; D-4 disposition.

## 6. Concrete public inspection/GUI effects (only from proposed real fields)

Zero-write, read-only surfaces unchanged in mechanism:

- **Automatic (data-driven, no code change):** `revoked` appears in `summary.evidence_statuses` and `work_detail` evidence `status` (`inspection.py:190-194`, `:303-315`); `EvidenceRevoked` rows appear in `events()` and `summary.event_types`.
- **Needs code + browser RED/GREEN (desktop/390/320 per AGENTS.md):** a `.chip-st-revoked` CSS class in `app.css:231-235` (status text already renders verbatim; without a class it falls to the default chip style — color is augmentation, meaning stays in the text, per DESIGN); optionally a derived "completion cites revoked evidence" line computed from `completion_raw` vs evidence statuses — derivation only, no stored field, no write endpoint.
- **Optional scope decision:** the summary tile counts only `pending_verification` evidence (`app.js:286-287`); a revoked-evidence tile is a new UI element, not a correctness need — recommend leaving it out of the core sprint or making it an explicit UI task with full browser checks.
- Docs owed (doc_sync_map): `runtime.py` → [runtime-boundaries](../../docs/runtime-boundaries.md) new "Evidence revocation boundary" section; command row in [interventions](../../docs/interventions.md) table (authority includes a `work.intervene` path); [verification](../../docs/verification.md) named-test section (like S3's, not blanket P-matrix rows); [gui](../../docs/gui.md) evidence-status note if the chip/derivation change lands.

## 7. Policy families, tests, installed demo

- **Both families with zero policy edits** (§1). Expense: revoking a verified `approval` (E05) makes `propose_action` reject `REQUIREMENT_UNSATISFIED` and a prepared op hold at dispatch (D-3 path) with zero external calls; revoking `accepted` (E08) blocks `request_completion` on an open work and demonstrates closed-work correction on a succeeded work. Publishing: revoking `approval` (C02) blocks `content.publish`; revoking `accepted` (C04) blocks completion; note `PublishingPolicy.has()` additionally requires the configured *source*, so replacement proofs must come from the current source, not merely carry the right digest.
- **Named tests the design owes** (beyond unit-shaped ones): malformed payload (`CommandError`); `EVIDENCE_UNKNOWN`/cross-work (`EVIDENCE_SCOPE_MISMATCH`)/stale version; double revoke (`EVIDENCE_ALREADY_REVOKED`); same-command replay returns stored receipt; **replay after authority loss returns fresh unpersisted `AUTHORITY_DENIED` and the stored receipt survives** (pins the `_replay_denial` branch); revoked-pending-then-`verify_pending` stays revoked; restart (`recover()`) does not revive; migration after revoke keeps revoked; resend after revoke returns the id with `evidence_status: "revoked"` and no new row; replacement proof under a new event id verifies and satisfies; waiting/triggered/cancelled/expired wait dispositions (no resurrection, no deadline reset); prepared intent held at dispatch/recover with **counted** zero external calls; revoke during in-flight → op confirms, exactly one external effect, new accepted proof under the operation id; confirmed-effect revoke retains `confirmed_succeeded`/`external_id`; closed-work correction (snapshot byte-stability, status stays closed, derived audit visibility); transaction crash rollback on the revoke path; a real process-death case per the sprint's crash standard. Existing 622+14 tests stay green; the only spec-visible change to existing receipts is the additive resend status field.
- **Installed demo:** a deterministic no-credentials `revocation-demo` (fresh stores per scenario, counted external effects, both families, printed inspect commands) following the intervention-demo pattern, plus a `verify_install.py` stage. Note for master: this adds a demo gate — AGENTS.md/supervibe gate wiring is master-owned and must be updated when the sprint is materialized.

## 8. Scope confirmations

No rewrite, no new dependencies, no tenant/auth framework, no new write UI or endpoint, no compensation claim: local revocation is a trusted-local decision over grants configuration (not authentication) and cannot fence an already-running external call — the residual external race remains exactly the one stated in RFC-001 §5.2 and [runtime-boundaries](../../docs/runtime-boundaries.md). Historical S7 evidence and release `48c01fd` untouched; this review changed no product code, docs or specs.
